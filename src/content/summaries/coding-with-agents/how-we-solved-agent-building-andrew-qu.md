Andrew Qu traces Vercel's internal data science agent, D0, from a large prompt to a sandbox-based agent, then explains how those lessons informed the Eve framework. His argument is that familiar tools plus company-specific knowledge can matter more than elaborate orchestration. This is a practitioner account, not a controlled architecture comparison.

Results below are Qu's reports, not independently verified benchmarks.

### Main points

- **Start with a recurring interruption.** Marketing and sales questions forced the data team to stop other work, write SQL, analyze results, and report back. Qu's first prototype put the Snowflake schema in a system prompt; he manually ran the generated SQL to test whether the model could produce useful queries. [02:36–04:22](https://www.youtube.com/watch?v=9dYcwOkpCE8&t=156s)
- **Preserve the context needed to recover from errors.** A chain of specialized agents automated the question-to-answer process, but each successor received only a summary and a small snippet of earlier work. Qu moved to one agent managing its own planning, execution, and reporting state so it could revisit earlier exploration when a query or join failed. This improved their prototype, yet the first limited rollout still exposed questions their evaluations had missed. [04:22–07:35](https://www.youtube.com/watch?v=9dYcwOkpCE8&t=262s)
- **Put the semantic layer in a sandbox and let the agent explore.** After seeing Claude Code with Opus 4.5 answer their questions, the team rebuilt around a file system containing company data definitions and relationships. Bash, file reading, and file writing let the agent find relevant context and work through the task; a few extra tools handled Vercel-specific needs. Qu attributes the improvement to tools the models already use well rather than a prescriptive custom tool set. He says the evaluation score roughly doubled, but the talk does not isolate the effects of model, tools, and context changes. [07:35–09:50](https://www.youtube.com/watch?v=9dYcwOkpCE8&t=455s)
- **Turn repeated query patterns into reusable skills.** With thousands of daily queries, the team found recurring shapes such as aggregations, product lookups, and billing questions. A recurring job distills recent queries into skills—roughly 100 at the time of the talk—so a new run starts with accumulated task knowledge, not only the system prompt and semantic layer. Qu does not explain the skill-generation or validation procedure in enough detail to reproduce it. [10:14–11:23](https://www.youtube.com/watch?v=9dYcwOkpCE8&t=614s)
- **Package the lessons as conventions, not another bespoke project.** Eve applies a Next.js-like file-system convention: skills, tools, and channels live in designated folders that the framework uses to assemble an agent. Qu describes a runtime with durability, isolated execution, model access, and connections, with adapters for alternative infrastructure and a Vercel deployment path. The team rewrote D0 in Eve to make its instructions, skills, and tools easier to compose and iterate on. [11:35–14:15](https://www.youtube.com/watch?v=9dYcwOkpCE8&t=695s)
- **Company knowledge is the differentiator.** Qu argues that useful data agents need more than access to Snowflake: they must know which business concepts relate and when to query them. He reports roughly 20 useful internal agents across functions and says D0 freed the data team to improve Snowflake performance and add missing data sources. These are reported organizational outcomes, not measured productivity estimates. [15:03–16:53](https://www.youtube.com/watch?v=9dYcwOkpCE8&t=903s)
