Theo reads and critiques an account of the Claude Code team's code-review process, comparing it with his work on T3 Code. The central problem is how to catch defects without turning increased agent output into more human waiting time or endless automated review. His strongest disagreement concerns recurring mistakes: improve the code and static checks before adding more written instructions.

This summary is based on the English auto-generated captions. Anthropic's results are first-party claims relayed in the video; Theo's T3 Code examples and model comparisons are practitioner reports, not independent evaluations. The video includes a Browserbase sponsorship.

### Key points

- **Measure human effort without hiding downstream failures.** The Anthropic account aims for most changes to need at most one human, potentially the author. It tracks approvals, comments, and time waiting on people, with revert and incident rates as checks against merely moving work into production failures. Theo adds that handoff delays and draining work matter alongside minutes spent reviewing. [08:32–11:40](https://www.youtube.com/watch?v=TFCDWrEBaFM&t=512s)
- **Give agents ways to demonstrate that a change works.** Before a human looks, run checks and have a fresh-context agent review the diff. Theo argues that builds, lint, and unit tests are insufficient for some changes: let agents run the application and exercise user flows. He describes using recorded UI interactions and pre-baked model events to test T3 Code without making additional live model calls for the simulated responses. These are his practices, distinct from the Claude Code process he is reading. [10:36–13:39](https://www.youtube.com/watch?v=TFCDWrEBaFM&t=636s), [15:32–16:30](https://www.youtube.com/watch?v=TFCDWrEBaFM&t=932s)
- **Fix recurring mistakes as close to the code as possible.** Theo's preferred order is clearer architecture, then static analysis such as lint rules and type checks, then prose instructions or skills when those approaches cannot address the problem. Written guidance still has a role, including updates when the repository changes, but should not compensate indefinitely for a confusing codebase. This differs from the article's emphasis on putting repeated review lessons into instruction files. [16:30–19:27](https://www.youtube.com/watch?v=TFCDWrEBaFM&t=990s), [39:23–41:12](https://www.youtube.com/watch?v=TFCDWrEBaFM&t=2363s)
- **Have agents evaluate feedback before asking humans to act.** Theo wants the coding agent to watch its pull request, judge review findings, and address valid ones rather than leave a person copying suggested prompts. The Anthropic account describes separate agents checking candidate findings, filtering noise, and requiring each remaining finding to be fixed or resolved with a reason. Blindly implementing every comment can inflate a small change into unnecessary code; more review layers do not automatically mean a better result. [14:41–15:32](https://www.youtube.com/watch?v=TFCDWrEBaFM&t=881s), [20:31–23:27](https://www.youtube.com/watch?v=TFCDWrEBaFM&t=1231s)
- **Make review loops converge.** Theo describes an unattended review loop that ran for days and expanded a change to roughly 80,000 lines. The Anthropic account also reports excessive rounds, then describes reconsidering the approach after three rounds, reviewing only the new diff after initial passes, grouping related bugs, and suppressing repeated findings. Theo experiments with reviewer scores instead of requiring zero comments, but acknowledges an alternative: have the agent decide whether each comment can be ignored. Neither approach is presented as a settled universal rule. [26:22–31:39](https://www.youtube.com/watch?v=TFCDWrEBaFM&t=1582s)
- **Match human approval to risk and retain accountability.** The described Anthropic policy uses zero, one, or two human approvals depending on risk, reserves lighter paths for trusted authors, and always requires a person for designated sensitive changes. Agent approvals do not fill human approval slots, and new commits can invalidate prior approval. Theo is interested in risk classification but questions the fixed tiers. Humans still own scope, architecture, evidence quality, and the outcome of the changes they initiate. [22:38–25:24](https://www.youtube.com/watch?v=TFCDWrEBaFM&t=1358s), [30:35–32:41](https://www.youtube.com/watch?v=TFCDWrEBaFM&t=1835s)
- **Use production failures to improve both detection and recovery.** The account combines a merge queue, internal rollout, staged release, and fast rollback. Confirmed incident-causing changes become evaluation cases for the reviewer; known-clean changes help reveal false positives that would prompt harmful edits. The team also tracks review rounds, because catching more issues is not enough if the reviewer creates unbounded work. Theo supports the emphasis on quick recovery rather than treating slower shipping as the solution. [25:24–27:25](https://www.youtube.com/watch?v=TFCDWrEBaFM&t=1524s), [28:29–30:35](https://www.youtube.com/watch?v=TFCDWrEBaFM&t=1709s)
- **Preserve shared understanding even when machines read most diffs.** Theo values review as a way to spread knowledge, not just catch bugs. The account has no formal replacement for that function, but describes targeted code explainers, interactive visualizations, and open team channels. People still decide whether a change should exist and can close or reshape it when a simpler direction emerges. Cheap code generation does not create an obligation to merge the result. [31:39–36:27](https://www.youtube.com/watch?v=TFCDWrEBaFM&t=1899s)
