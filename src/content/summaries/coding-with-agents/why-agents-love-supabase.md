Supabase co-founders Paul Copplestone and Ant Wilson talk with swyx about the announcements they had prepared for the Supabase Select conference and about how coding agents changed Supabase's business. Their agent-related argument is that agents now do much of the work at the start of a project: they sign users up, create databases, and need to read the database's current shape from files. This material is spread through the roughly 71-minute interview. Most of the conversation covers other topics: Postgres engineering (the OrioleDB storage engine and Multigres for sharding), company history, Hacker News launches, memes, a community stock grant, and sales.

In his added intro, swyx says he was an angel investor in Supabase's seed round and that Supabase is Latent Space's first sponsor.

### Key points

- **Agents now complete the sign-up work.** The founders describe three AI phases for Supabase: using Postgres as a vector database for embeddings; the vibe-coding wave of late 2024 with tools such as Lovable and Bolt; and 2026, when better models drove a fast rise in sign-ups with little marketing spend. They say consumer-like traffic usually lowers activation and paid conversion, but both rose because the agent takes the user from sign-up to activation in one step. They describe that activation rate as "almost 100%" and say these users convert to paid at a higher rate than traditional developer users. They give no conversion figures. [30:17–34:25](https://www.youtube.com/watch?v=zHG6sAss_kE&t=1817s)
- **Agent-built projects also make money sooner.** Earlier, customers chose a database, built a product, and added billing later. The founders say Stripe billing can now be added through the agent, so some projects earn serious money in their first week. One customer earned about $10,000 in the first few days, which convinced them vibe coding would last. [29:14–30:17](https://www.youtube.com/watch?v=zHG6sAss_kE&t=1754s)
- **Many small databases need a cheap start and a path to grow.** Supabase launches about 5 million databases a month and expects to need billions. The founders say a dedicated Postgres cluster for each would use up the available compute. They announced the acquisition of Turso, which built multi-writer concurrency on top of SQLite, because they see a path to Postgres compatibility on Turso's file format. A new small instance type, Supabase Spark, is meant to work with Supabase's libraries and upgrade to full Postgres, and later Multigres, when a project grows. They call zero-downtime migration between these backends a requirement, because non-technical founders, such as a teacher who started the company Magic School, now build whole companies. They also say Supabase could not previously handle the scale of being the default backend inside a large chat app: if each of ChatGPT's roughly 1.2 billion monthly users launched one database a month, that would mean 1.2 billion Postgres servers. They expect the Turso technology to change that. The interview does not explain how the upgrade path works. [12:37–17:38](https://www.youtube.com/watch?v=zHG6sAss_kE&t=757s), [55:36–56:40](https://www.youtube.com/watch?v=zHG6sAss_kE&t=3336s)
- **Declarative schema files give agents the current database shape.** Postgres projects usually record each schema change as a new file in a migrations folder, which works as a historical log. The founders explain that an agent asking for a table's shape must then reason across what could be a thousand migration files, or start a local database, run every migration, and inspect the result, which is too slow. Supabase's CLI creates a `supabase` folder that represents the project as code. With the change announced at Select, its schemas folder can describe the full database declaratively, including tables, policies, and database comments. Supabase is also releasing pg-delta, a library that works with any Postgres database. Their reason is that agents mostly work on code and need to iterate quickly on the file system. The interview does not explain how edits to these files become migrations applied to a database. In his intro, swyx adds that keeping the schema in Git as the source of truth lets an agent read and fork it, and that people benefit too. [58:20–1:01:17](https://www.youtube.com/watch?v=zHG6sAss_kE&t=3500s), [01:50–03:55](https://www.youtube.com/watch?v=zHG6sAss_kE&t=110s)
- **Platform skills stopped early agents from misusing the database.** Early agents stored image data in Postgres and turned off row-level security (RLS), the per-row access policies, to get projects working. The founders credit Lovable with first writing good skills to stop this, and the speakers say current models no longer make these mistakes. The skills themselves are not described. [46:08–48:17](https://www.youtube.com/watch?v=zHG6sAss_kE&t=2768s)
- **Compute next to the database removes the function time limit.** Supabase Edge Functions run on Deno and have a short time limit, and users wanted longer jobs such as chunking documents and creating embeddings. Supabase Compute runs any container, including Rust, Python, or an agent, as a long-running serverless workload on the same private network as the database. Community members had tried to build durable workflow engines on Edge Functions and failed because of the timeout. The founders present Compute as the building block for such workflows, not a workflow product. [06:03–08:08](https://www.youtube.com/watch?v=zHG6sAss_kE&t=363s), [53:54–54:48](https://www.youtube.com/watch?v=zHG6sAss_kE&t=3234s)
- **The founders can only partly explain why models recommend Supabase.** swyx says his tracker shows frontier models recommending Supabase as their first choice for an integrated backend: auth, functions, database, and APIs together. He attributes this to timing, since Supabase had three to four years in the market before LLMs took off. The founders call the timing an accident and add years of community blog posts, videos, and podcasts that they are "sure" ended up in model training. The conversation also credits Supabase being open source. The founders say they now invest heavily in this and want partnerships with frontier labs, mainly in the US. None of this is tested in the interview. [33:22–35:22](https://www.youtube.com/watch?v=zHG6sAss_kE&t=2002s), [54:48–55:36](https://www.youtube.com/watch?v=zHG6sAss_kE&t=3288s)
- **Coding agents make code rewrites easier, but production database migrations stay risky.** swyx suggests coding agents could finally let companies move off legacy software. One founder agrees that rewriting the million-line stored procedures that keep Oracle customers in place is probably easier now. The founders say the harder problem is the transactional database behind the main revenue-generating application: downtime costs money, and running old and new databases in parallel risks a split brain, where the two hold conflicting data. Teams therefore usually put new workloads on the new database. Supabase focuses on new projects because it saw earlier database companies fail at selling migrations. [48:17–51:05](https://www.youtube.com/watch?v=zHG6sAss_kE&t=2897s), [43:11–45:16](https://www.youtube.com/watch?v=zHG6sAss_kE&t=2591s)
- **Supabase's internal AI spend is about $300,000 a month for 450 people.** Each team chooses its own AI tools, with some recent consolidation for cost. swyx offers a rule of thumb: compare token spend with salary spend; about 0.1 is common, up to 1 is probably safe, and above 1.5 is probably trouble. The founders have a spend leaderboard but say spend is the wrong focus. They want to count end-to-end processes that no longer need a person, or long tasks that become short. Because Supabase works asynchronously and writes everything down, they can point AI at the company's history, for example to write down its decision-making principles. They call this building a company harness. [1:10:51–1:14:50](https://www.youtube.com/watch?v=zHG6sAss_kE&t=4251s)
- **Two open concerns: convergence and operations.** One founder still pushes his own engineering opinions on agents but finds this less and less necessary. He worries that agents will then settle on one way of building software, losing the debates through which better approaches win. swyx expects skilled developers to keep caring about details; the founder questions how those developers will be trained. Both agree that AI has not yet solved site reliability engineering, because keeping systems running is a different problem from building software.
