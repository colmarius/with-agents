Max Kanat-Alexander answers "does code quality still matter?" by looking at what code quality was for in the first place. He argues that it exists to help people understand a system and change it safely. Rigor therefore matters in proportion to how durable the software is. He also proposes two newer kinds of engineering work: making some software safely disposable, and making rigor cheaper for everything else.

The talk is a conceptual framework drawn from his experience. Its claims, including the forecast that disposable software will become far more common than durable software, are arguments and predictions, not measured findings.

### Key points

- **Code quality serves understanding and safe change.** Kanat-Alexander says all software success depends on understanding a system and executing on that understanding; debuggers, observability, evals, and tests exist to support one or both. For engineers, the two key questions are what the system actually does, as opposed to what its documentation says, and how to change that behavior correctly and safely. He states this strongly: code quality is "only" for these two purposes, not for correctness as a separate goal. [00:55–02:52](https://www.youtube.com/watch?v=bU5gDVyu_28&t=55s)
- **Structure is what makes large systems understandable.** No one can describe the full behavior of a system as large as Chromium, but people can describe a component such as its URL parser. He contrasts a recognizable "Hello World" program with an unstructured sequence of instructions that prints the same output. The second is readable at that size, but would be very hard to follow at millions of lines. In his view, readability and testability mattered because they gave a system understandable structure. [02:52–04:38](https://www.youtube.com/watch?v=bU5gDVyu_28&t=172s)
- **Every change risks a problem now and more risk later.** A change can introduce a problem, which he defines broadly to include bugs, delays, budget overruns, and behavior users did not want. It can also make the system harder to understand, which raises the risk of future changes. He says he can trace every postmortem he has read to these two causes. Because the second risk feeds the first, difficulty compounds non-linearly until every modification causes some problem. [04:38–06:21](https://www.youtube.com/watch?v=bU5gDVyu_28&t=278s)
- **Disposable software is the case where quality does not matter.** He sets aside whether future models will handle unlimited complexity. Instead he argues that models are making disposable software, which has always existed, vastly more common. Software is disposable when failure has little consequence, few people or systems depend on it, it costs almost nothing to replace or maintain, and change management barely matters. A personal calculator or a party planner for one event are his examples. In that case the compounding risks do not arise, so code quality does not matter. [06:21–08:04](https://www.youtube.com/watch?v=bU5gDVyu_28&t=381s), [08:56–09:54](https://www.youtube.com/watch?v=bU5gDVyu_28&t=536s)
- **Durable software still needs full rigor and will grow.** Durable systems live for years, serve many people, have potentially catastrophic failure costs, and need heavy maintenance. He expects them to remain the most important systems and to increase in absolute number, because AI tools also make durable software easier to build. He calls the claim that durable engineering is going away the biggest confusion he sees on social media. [07:15–08:56](https://www.youtube.com/watch?v=bU5gDVyu_28&t=435s), [10:47–11:44](https://www.youtube.com/watch?v=bU5gDVyu_28&t=647s)
- **Place software on a spectrum, and err toward durable.** Consequences, cost of replacement, dependencies, and cost of maintenance determine where a system sits between disposable and durable, and how much rigor it needs. He advises assuming these factors are higher than they appear. [08:56–09:54](https://www.youtube.com/watch?v=bU5gDVyu_28&t=536s), [11:44–12:43](https://www.youtube.com/watch?v=bU5gDVyu_28&t=704s)
- **Teams can deliberately make software more disposable.** His proposed techniques are isolated environments without customer or personal data; enforced independence, such as blocking inbound calls from other production systems; redundancy, where a clunky but durable backup remains available when a vibe-coded front end fails; and narrow scope. He presents this as a possible new engineering discipline, not an established practice. [09:54–11:44](https://www.youtube.com/watch?v=bU5gDVyu_28&t=594s)
- **Reduce the cost of rigor so misjudging durability is cheap.** Because no one will always classify software correctly, he argues that making rigor cheap matters more than choosing the right point on the spectrum. If rigor is cheap, a project that turns out to need durability can be upgraded easily. [11:44–12:43](https://www.youtube.com/watch?v=bU5gDVyu_28&t=704s)
- **His examples of cheaper rigor.** Standardizing languages, frameworks, and RPC protocols removes possibilities: with no PHP in the system, no one needs PHP linters or PHP security practices. "Inward flow tooling" runs automatically, quickly, and reliably, with few false positives, so developers do not have to choose to run it; if it is cheap enough, it can apply to disposable software too. Test infrastructure should make every test fast and deterministic without expertise; he notes that a coding agent can now build in-memory fakes of services, but someone must decide to provide them to everyone. Maximum lint strictness from the start avoids debates and later large cleanup changes, provided false positives are rare and not costly. [12:43–15:27](https://www.youtube.com/watch?v=bU5gDVyu_28&t=763s)
- **His answer.** Code quality does not matter for disposable software and does matter for durable software. It does not have to be expensive. [15:27–16:14](https://www.youtube.com/watch?v=bU5gDVyu_28&t=927s)
