David Ondrej describes how he builds, reviews, and ships software when agents write all of his code. The main rules are to keep one task per agent thread, review larger changes with a frontier model from a different lab, use sub-agents only for predictable parallel work, and automate repetitive work as small agent loops that hand uncertain cases back to a person.

This summary is based on the English auto-generated captions. The channel is David Ondrej's, and he introduces himself by name; the captions rendered the name and several product names phonetically, and those were corrected in the transcript. Ondrej built Cloudroom, the open-source agent workspace he uses throughout the video and promotes repeatedly. Its feature, speed, and "first" or "only" claims are first-party claims. His productivity figures, loop counts, and error-reduction percentages are self-reported and unmeasured. Model names, rankings, and subscription advice reflect his preferences when he recorded the video.

### Key points

- **Learn broad architectural concepts rather than syntax.** Ondrej argues that recognizing languages or memorizing syntax matters less than knowing concepts such as trade-offs, caching, observability, blast radius, and coupling and cohesion. The goal is to recognize, for example, that an instant page change might come from preloading or caching, then direct the agent accordingly. He suggests using AI to learn any unfamiliar concept. [04:42–06:48](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=282s)
- **Give each thread one task, and reproduce bugs before fixing them.** He keeps each agent session to one feature, bug fix, or investigation, and forks a new session for anything else. For a bug, the agent first reproduces it end to end as a user would, through a test, simulation, or experiment, rather than working from a vague description. For UI changes, he asks for screenshots of the running app before accepting the fix. [08:42–10:43](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=522s)
- **Use skills for large or risky changes.** Repeated short prompts live in text snippets; longer procedures become skills. His "4x4" skill asks him four sets of four questions about product, software design, practical concerns, and edge cases before a big change. A "risky changes" skill, which agents trigger on their own, adds a safety check for changes that could hurt customers. He says it exists because a filter once disabled 99% of a feature on live data, and that most of his skills come from similar costly mistakes. Small, obvious changes skip these steps. [10:43–12:52](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=643s)
- **Limit agent-written tests.** Ondrej tells agents not to write tests unless necessary, because he considers most agent-written tests filler that slows the project without catching real problems. When agents repeat the same class of mistake, he asks for one or two targeted tests to prevent it. He says agents still write some tests despite the instruction, which he treats as about the right amount. This is his opinion; the "over 90%" figure he gives is not measured. [12:52–14:48](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=772s)
- **Review with another lab's model, then triage the findings.** He builds with Claude Opus 5.5 at high reasoning effort and reviews medium or large changes with an OpenAI frontier model, or the reverse if you build with OpenAI. For very large changes, a slower "total review" skill sends the change to several labs' models and returns one deduplicated list. He warns against rerunning reviews repeatedly: a model asked to find bugs will report something even when no serious bug exists. Findings are rated by how often they would occur and how bad they would be, and he asks the building model whether each one is "a real must-fix issue or overthinking." He uses a further review only when that answer is unclear. He says this workflow assumes frontier models and will not transfer to small or cheap ones. [13:45–18:48](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=825s)
- **Ship directly, and use loops to catch side effects.** After review, he pulls, rebases onto main, runs CI, and ships to production. Agent loops then check recent changes for side effects and security problems; he estimates they catch 95% of side effects but gives no measurement. He scopes this pace to early-stage products and says teams with thousands of paying customers need more care. [17:52–18:48](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=1072s), [18:48–19:52](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=1128s)
- **Aim for agents to write all of the code.** His argument is arithmetic: if agents handle half the work, the manual half still sets the pace, so the gains stay small until agents write and review everything. He states that he does not mind agents breaking production as long as they fix it quickly. He reports about 700 production commits per week and says he quantifies output to check that AI work is productive rather than internal tooling. This is his stated stance, not evidence that unattended production changes are safe. [06:48–07:51](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=408s), [19:52–22:59](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=1192s)
- **Use sub-agents only for clear, parallel, predictable work.** Sub-agents suit tasks such as reading 2,000 documents or session logs, where the input, process, and output format are all known. A capable main agent can then run cheaper models such as Haiku on each chunk. Most software work involves surprises, such as a small bug fix that turns out to touch billing, so he uses a single top-level agent on the strongest model for it. His rule is that if you are unsure, do not use sub-agents. He also estimates that heavily parallel modes can use up a subscription about five times faster for a 1.5x to 2x speedup. [21:57–27:02](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=1317s)
- **Run most agents in their own cloud sandboxes.** Agents in one checkout can edit the same files. Worktrees separate their files but, in his account, consume disk space and still share the machine's CPU, memory, and screen, so heavy tests or browser automation disrupt the person at the computer. He prefers one isolated cloud sandbox per agent. The benefits he cites are separate resources, scaling to many agents, containing a compromised sandbox, and work that continues when the laptop is closed. He reports that 64% of his open threads run in the cloud and predicts 90% or more. He attributes developers' preference for local agents to cloud setups missing skills, API keys, dependencies, or repositories. [29:07–35:10](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=1747s), [37:14–39:08](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=2234s)
- **Demo: let cloud agents reach the laptop under a set access level.** Cloudroom preloads selected skills, MCP servers, and API keys into each sandbox. It also lets a cloud agent read files on his Mac at one of four access levels: full, read-only, ask, or off. In the demo, a cloud agent counts the files in his Downloads folder. **Editorial note:** full access from a cloud sandbox to the laptop reduces the isolation he cites as a security benefit, so the access level needs the same care as any other credential. [34:07–37:14](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=2047s)
- **Choose an agent workspace that agents can control.** His criteria are support for all major harnesses, use of the model subscriptions you already pay for, and a command-line interface through which agents can start, inspect, stop, and archive other threads. He demonstrates an Opus agent starting Haiku sub-agents, stopping them, and launching five top-level Codex threads on a different model. He argues that model labs' own apps will not support competing models. These criteria come from the builder of a competing product. [39:08–45:02](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=2348s)
- **Build a "software factory" one small loop at a time.** An agent loop here is a recurring agent task that runs with little or no human involvement. He recommends starting with one or two loops for boring, predictable work and building your own rather than copying another person's skills or loops. His analogy is Minecraft: automate chopping wood, and keep building the cathedral, the creative and judgment-heavy work, for yourself. His bug loop has Opus confirm and fix a reproducible bug, then asks a model from another lab for an adversarial review. If both agree that the bug is real and the fix is clear and safe, it ships. He reports 33 loops, about 2,000 runs per day, and 86% running without him, and alternates models because different models find different problems. [45:02–48:03](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=2702s), [48:03–50:02](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=2883s), [50:02–53:01](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=3002s)
- **Find candidate loops in your own session history.** Past agent sessions record your prompts, skill sequences, and problem-solving habits. His Cloudroom "scan" splits that history among about 30 Haiku sub-agents to find repeated workflows; he presents this as the predictable, chunkable case where sub-agents fit. Each suggested loop uses what he calls a 10/90 split. The safest, most obvious 10% of cases run autonomously. For the other 90%, the loop researches and proposes an action, then waits for approval. Suggestions he shows include a daily release check, a sweep of old threads, and a morning cleanup of pinned threads. [53:01–58:45](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=3181s), [59:49–1:02:57](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=3589s)
- **Judge output by a public changelog, not commit counts.** He suggests asking people who report large numbers of PRs, commits, or Markdown files to show a public changelog of what actually shipped. [58:45–59:49](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=3525s)
- **Route user feedback into agent threads.** Users, or their agents, report bugs and ideas through a button or CLI command that writes to a Postgres table. A loop checks the table every minute and opens a thread in which an agent investigates the report without editing code. Duplicates, noise, and already fixed issues are archived automatically; real problems become GitHub issues with a short summary. Reporters build a reputation, so the agent treats reports from known spammers more strictly. After Ondrej or a developer approves, an agent fixes the issue, another lab's model reviews the fix, and it ships. He says this usually fixes reported bugs within 24 to 48 hours; the pipeline is his internal setup, not a released feature. [1:08:42–1:15:42](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=4122s)
- **Keep local models for privacy, unrestricted use, and resilience.** He runs DeepSeek on his own DGX Spark machines for legal contracts, employee data, and other sensitive material, so that material does not go to model providers. He also uses local models for unrestricted queries and as a fallback if he lost access to hosted models. He uses frontier hosted models for hard coding work. His predictions about hardware value and rising prices are forecasts. [1:15:42–1:24:53](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=4542s)

### Limits

The video is a single practitioner's account and a long product demonstration. Its percentages and rates, including review catching most problems and agents fixing bugs within a day, are not measured or compared with alternatives. The direct-to-production practice depends on frontier models, an early-stage product, and his tolerance for production breakage. Model rankings and subscription advice were current when he recorded and are likely to change. [00:52–03:48](https://www.youtube.com/watch?v=F8rc-ULd4_4&t=52s)
