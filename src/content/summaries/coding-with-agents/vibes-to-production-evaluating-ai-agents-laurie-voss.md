Laurie Voss teaches an introductory evaluation workflow for agents in a two-hour workshop. He instruments a small financial-research agent, reads its traces, and builds code checks and model-graded checks. He then tests whether the model grader agrees with human labels and uses failing cases to drive measured prompt changes. Most of the method transfers to other tools; the hands-on steps use his employer's platform.

This summary is based on the English auto-generated captions. Voss introduces himself as head of developer relations at Arize AI and a former npm co-founder. The workshop runs on Arize AX, so claims about its setup effort, compatibility, built-in evaluators, skills, and in-product agent are vendor claims; it does not compare AX with other tools. The demo agent uses deliberately weak prompts and about a dozen queries, and some demo labels were assigned at random, so its scores illustrate the steps rather than measure anything.

### Key points

- **Traces record what happened; evals judge whether it was good.** Voss calls evals "testing for AI" and traces "logs for AI." A trace is a tree of spans. Each LLM call, tool call, and full agent turn is a span with inputs, outputs, timing, and token counts. Shipping after a few manual queries fails because three runs are not a test suite. Unit tests with exact expected strings also break down because the same prompt produces different, possibly equally correct, text each run. Evals turn quality into a number that can expose a prompt change that fixes tone but adds hallucinations. They can also show within hours whether a new model is better. [07:12–11:08](https://www.youtube.com/watch?v=qZj7sqmidqA&t=432s)
- **Use code evals, model judges, and humans for different jobs.** Code evals are deterministic functions, such as checking that output parses as JSON or stays under a length limit. They are fast, cheap, and reproducible, but brittle when correct answers are worded differently. An LLM-as-a-judge eval uses a second model and a rubric to grade semantic questions such as accuracy or tone. It costs money, is itself nondeterministic, and must be calibrated against people. Human review is the quality standard but slow; Voss cites an unsourced figure that fatigued annotators miss up to 50% of defects. He also distinguishes capability evals, which are expected to fail at first and give the agent a target, from regression evals, which should nearly always pass. [11:08–14:19](https://www.youtube.com/watch?v=qZj7sqmidqA&t=668s), [17:15–18:17](https://www.youtube.com/watch?v=qZj7sqmidqA&t=1035s)
- **Agents need checks on intermediate steps and room for valid alternatives.** Each tool call and decision adds a chance to go wrong, so Voss checks tool choice, arguments, stopping, and loops. Multi-agent systems also need checks on handoffs. In his cascading-failure example, an agent researches "Tesla" the inventor instead of the company, and every individual step looks correct. Agents can also be creatively correct: he reports that in Anthropic's tau-squared bench run, an agent upgraded an economy flight to first class so it could reschedule it, then failed the test. He therefore recommends grading what the agent produced rather than requiring a specific tool sequence. [14:19–17:15](https://www.youtube.com/watch?v=qZj7sqmidqA&t=859s), [57:25–58:17](https://www.youtube.com/watch?v=qZj7sqmidqA&t=3445s)
- **Read traces and write success criteria before writing evals.** Voss calls this the most important practice in the workshop. Reading a dozen or more traces showed that 3 of his 13 runs tried to write the report to a disk that did not exist in the notebook. Those runs returned a summary saying the report was saved. Other runs looped through searches or made claims that the research did not verify. He recommends writing the criteria for a good report with product, QA, and support staff who know the domain. Use open coding first, writing each failure in plain language, then axial coding to group failures into root causes such as retrieval, reasoning, hallucination, or scope violations. Prioritize by severity as well as frequency. [33:47–35:40](https://www.youtube.com/watch?v=qZj7sqmidqA&t=2027s), [38:41–41:38](https://www.youtube.com/watch?v=qZj7sqmidqA&t=2321s), [42:41–48:36](https://www.youtube.com/watch?v=qZj7sqmidqA&t=2561s)
- **Make test queries look like production traffic.** Before real traffic exists, an LLM can generate varied phrasings of the same intent, plus edge cases such as nonexistent tickers, multi-part questions, and jailbreak attempts. A domain expert should review the queries because generated queries cluster around obvious wording. Replace synthetic data with production data once you have it. [41:38–43:44](https://www.youtube.com/watch?v=qZj7sqmidqA&t=2498s)
- **Start with a cheap code check and layer other evals on top.** His first eval checks whether the requested stock ticker appears in the report. It caught a subtle failure: a query about AWS profitability produced a report about AWS alone that never named Amazon's ticker. Code evals can still be sophisticated, such as querying an API for the real stock price, as long as the same input always gets the same grade. Voss uses the Swiss cheese model from safety engineering: each layer misses some failures, so stack code checks, model judges, and human review. [48:36–50:19](https://www.youtube.com/watch?v=qZj7sqmidqA&t=2916s), [54:15–57:25](https://www.youtube.com/watch?v=qZj7sqmidqA&t=3255s)
- **Choose a judge that has the information it needs.** A built-in correctness eval, using Claude Sonnet 4.6 to judge Claude Haiku, scored all 13 reports as incorrect. The judge relied on its training data and objected that facts from the agent's live 2026 web research came from a future it could not know. A faithfulness eval instead gives the judge the agent's research output as context and asks whether the report stays grounded in it. That run marked 7 reports unfaithful and 6 faithful. Voss's lesson is that correctness suits other applications; the eval must match the question being asked. [58:17–1:06:17](https://www.youtube.com/watch?v=qZj7sqmidqA&t=3497s)
- **Write custom rubrics with observable, binary criteria.** Built-in templates could not check whether a report gave actionable buy, sell, or hold guidance, so Voss wrote a custom judge. He recommends giving the judge context about its role and listing specific pass and fail criteria drawn from error analysis. Wrap inputs and outputs in XML tags so the judge does not confuse data with instructions. He also adds good and bad examples, while noting that some practitioners think examples cause overfitting and that rigid examples reduce variety. Set labels as output choices outside the prompt, because AX has the judge return a label through a tool call. Prefer pass or fail over 1–5 scales, and ask the judge to explain its reasoning before scoring. [1:05:24–1:13:08](https://www.youtube.com/watch?v=qZj7sqmidqA&t=3924s), [1:13:08–1:14:11](https://www.youtube.com/watch?v=qZj7sqmidqA&t=4388s)
- **Avoid common rubric anti-patterns.** Treat eval prompts like code: version them, because small wording changes can shift results, and test them on known answers. Avoid a single "god evaluator" that checks accuracy, tone, completeness, policy, and format at once, because a failure does not say which dimension failed. Use one evaluator per dimension. Separate guardrails, which block shipping and may page someone, from north-star metrics that teams review weekly. [1:17:12–1:20:06](https://www.youtube.com/watch?v=qZj7sqmidqA&t=4632s)
- **Evaluate the judge as a classifier.** Domain experts label outputs to build a golden dataset; then compare the judge's labels with theirs. Keep tasks unambiguous, keep a reference solution that passes, and test both whether a behavior occurs and whether it is correctly skipped. Tune the rubric on about 75% of labels and hold out 25% to check generalization. His 46% agreement figure came from deliberately random human labels. The method is to read disagreements, decide whether the rubric or the person was wrong, and tighten ambiguous criteria. He usually favors recall over precision. He warns about position, length, confidence, and self-preference biases, and recommends judging with a different model, ideally from another lab. He says human inter-rater reliability can be as low as 0.2 or 0.3, so occasional disagreement is expected, while constant disagreement is a warning. [1:20:06–1:30:59](https://www.youtube.com/watch?v=qZj7sqmidqA&t=4806s)
- **Use experiments to test fixes against fixed datasets.** Save failing traces as a dataset and passing ones as a regression set. Voss had Claude read the judge's explanations and the requirements, rewrite the research and writing prompts, and rerun the agent and evaluators as an experiment. In the demo, the failure set became fully actionable; he says real iteration will be slower and should show gradual improvement over many runs. Fixed inputs and evaluators remove one source of variation, but the agent's web searches remain nondeterministic. [1:30:59–1:39:48](https://www.youtube.com/watch?v=qZj7sqmidqA&t=5459s)
- **Size samples and order fixes by impact.** He treats 12–20 examples as directional and suggests 200–400 for shipping decisions; halving the margin of error requires four times as many samples. Fix data quality first, then prompts, then model choice, and tune temperature or top-p last. He recommends writing an eval before building a feature, as in test-driven development. [1:39:48–1:42:23](https://www.youtube.com/watch?v=qZj7sqmidqA&t=5988s)
- **Close the loop in production.** Online evals run on sampled production traces at span or trace scope; monitors alert people, and new failures become regression cases. When a coding agent fixes failures across a repository, Voss sets two guardrails. Give it the requirements so it does not make evals pass by copying test data, and ask it to fix shared themes rather than individual traces. His suggested first step is small: add tracing, spend 15 minutes reading outputs, then write one code eval. [1:42:23–1:45:32](https://www.youtube.com/watch?v=qZj7sqmidqA&t=6143s), [1:46:26–1:49:37](https://www.youtube.com/watch?v=qZj7sqmidqA&t=6386s)

### Limits

The workshop is a 101 tutorial built around one vendor's platform. The method does not depend on Arize, but the two-line instrumentation, judge-tool mechanics, Alex agent, skills plugin, and sampling controls are described only as AX features. The demo results come from 13 traces with intentionally weak prompts and deliberately mismatched human labels, and the one-shot prompt improvement is not representative, as Voss says himself. The statistics on annotator fatigue and inter-rater reliability are cited without sources in the talk.
