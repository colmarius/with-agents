Lucas Meijer joins Mayank Gupta on The West Coast Builders to discuss how coding agents are changing programming work. Meijer was a contract game programmer for about ten years, then spent about 16 years at Unity, which he says grew from roughly ten people to a large company while he was there. He now works on independent projects, including Agents in the Cloud, his tool for running several coding agents in separate sandboxes. The practical material covers when to review generated code closely, why he runs agents away from his laptop, and how to automate bug-report reproduction, bisection, and exploratory product testing while a person approves each fix.

### Main takeaways

- **Agents that can rewrite software may make new languages viable.** [10:50–13:48](https://www.youtube.com/watch?v=D_or7cP7-Nw&t=650s): Meijer is optimistic that agents will change which programming languages are popular. He says agents have shown they can reliably rewrite existing software, and argues that this opens a window for new languages based on newer ideas, because rewriting large parts of the software that runs the internet used to seem impossible. He cites Bun's rewrite from Zig to Rust as the start of this. To try it himself, he had an agent rewrite 37signals' Campfire into Jai, Jonathan Blow's language, whose compiler is still in private beta, and models know almost nothing about it. He says the agent did an amazing job. [17:18](https://www.youtube.com/watch?v=D_or7cP7-Nw&t=1038s): seeing the Ruby-to-Jai rewrite run on his own computer affected him more than reading about such rewrites online. This is one anecdote; he does not say how the rewrite was tested or compared with the original. [09:45–10:50](https://www.youtube.com/watch?v=D_or7cP7-Nw&t=585s): he expects knowledge of how hardware, CPUs, and memory work to stay valuable, while the most popular language of the day is unlikely to stay on top.
- **Review depth depends on whether the code is the product.** [16:26–19:28](https://www.youtube.com/watch?v=D_or7cP7-Nw&t=986s): Meijer says it is hard to tell where agentic coding is going, because it changes so rapidly, and online accounts also range from claims of thousands of agents where everything is magic to his own experience that results are sometimes unimpressive. He works at different points on a spectrum, from not reading any code to slowly handcrafting every line, and chooses a point for each task. He has noticed that fast-moving people tend to build applications, while slow, line-by-line reviewers tend to write libraries. He says that if he wrote a library he would be more deliberate, because in a library the code is the product and other people build on it, so it cannot simply be changed later. In an application the product is the user's experience, so the code behind it can be replaced when needed. [18:24–20:23](https://www.youtube.com/watch?v=D_or7cP7-Nw&t=1104s): he says he used to think of himself as a very good programmer but no longer does; he now tries to be effective with agents, and finds that what works in which situation is hard to work out and keeps changing.
- **He runs several agents at once, isolated from his laptop.** [19:28–23:46](https://www.youtube.com/watch?v=D_or7cP7-Nw&t=1168s): although he takes the deliberate approach for most tasks, Meijer wants about seven agents running at once so he can move to the next task instead of waiting. With an unmodified Pi or Codex on his laptop, each task meant a terminal, a browser, and an editor window; he lost track of windows and edited code in the wrong one. Conductor was the first product he found that made parallel work convenient. He then wanted agents to keep working after he closed the laptop, and was uncomfortable running them in YOLO mode, without approving each action, on a machine that holds his secrets, family photos, and payment details. Agents in the Cloud gives each task its own sandbox and lets him talk to the agents from his phone. Despite the name, he says most users run it on their own hardware, such as a Mac mini, rather than in a cloud.
- **A software factory can start with one repetitive queue.** [24:40–28:43](https://www.youtube.com/watch?v=D_or7cP7-Nw&t=1480s): asked what a software factory is, Meijer says everyone defines it differently and points to the boring, repetitive work of shipping and maintaining software. At its largest, Unity had about 50 junior QA engineers processing incoming crash and bug reports: a high volume of mostly low-quality reports with some very good ones mixed in. Their job was to reproduce each report, rewrite it so a programmer could understand the actual problem, list the steps to reproduce it, and sometimes bisect, for example finding that the bug appeared between Unity 5.1 and 5.2; he adds that a finer bisection could even find the specific commit. He says companies with that kind of inflow should automate these steps, because the good reports point to real problems that many users hit. His recipe is to spend a day writing a prompt that takes one incoming report through every step, and to give the agent tools to build old versions or download prebuilt ones to bisect against. He presents this as simple, low-hanging work rather than a complicated system. It is a recommendation; he does not report running it or its accuracy.
- **An agent without source access can test the product like a new user.** [27:47–29:41](https://www.youtube.com/watch?v=D_or7cP7-Nw&t=1667s): for his own web application, Meijer recently started asking an agent with no access to the source code to install the product by following the website's instructions, use it as a user would, and produce a continuous stream of findings. He says this finds a lot of problems and that the prompt is short. He does not describe how he checks or filters the findings.
- **Proposed fixes can arrive as evidence for a person to approve.** [28:43–31:26](https://www.youtube.com/watch?v=D_or7cP7-Nw&t=1723s): Meijer suggests feeding the testing agent's findings into the report-processing loop, so that another agent proposes a fix for each one. A developer then starts the day with a queue in which each item shows the user's problem, a video of it, where the code broke, the proposed fix, a video after the fix, the diff, and a review agent's comment, and waits for approval. He describes approving such items one at a time and says this saves attention for higher-value work. He leaves the storage format open; pull requests are one option, though he says he has not used them in a long time.
- **The high-value work is deciding what to build and getting it used.** [31:26–32:16](https://www.youtube.com/watch?v=D_or7cP7-Nw&t=1886s): Meijer names deciding what to make and how to make it popular as the remaining high-value work. He treats product and marketing as one problem, because a product only has value if people use it.
- **He does not know what happens to programming jobs.** [32:16–35:09](https://www.youtube.com/watch?v=D_or7cP7-Nw&t=1936s): Meijer questions the premise that agents now do most of the work reliably and says predictions are hard. He expects much more small software: problems once too small to justify a custom build costing around $100,000 can now get their own tools, possibly generated from simple descriptions. He does not know how this extra demand for software and the reduced need for programmers to write each piece will balance out. [35:09–37:12](https://www.youtube.com/watch?v=D_or7cP7-Nw&t=2109s): he expects eager, forward-leaning people to do well, and the world to need fewer people who wait for Jira tickets and work through them one by one, adding that maybe that is okay.
- **He expects shared agent threads next.** [39:45–40:34](https://www.youtube.com/watch?v=D_or7cP7-Nw&t=2385s): Agents in the Cloud is built for individuals. Meijer expects a natural progression toward several people working with the same agent thread. This is a forecast.

### Practical interpretation

Editorial synthesis: Meijer's Unity example gives a bounded first automation target. Pick one incoming queue, write down the steps a QA engineer follows, and give the agent a way to build or download old versions so it can bisect. Keep a person approving each proposed fix, and judge the pipeline by whether its reproductions and bisections hold up, since the interview reports no accuracy or error rates.
