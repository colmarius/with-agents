Thorsten Ball presents coding agents as participants in the whole software-delivery lifecycle, not just replacements for typing code. His workflow combines asynchronous delegation, executable evidence, repository instructions, and access to operational tools. The examples come from building Amp; they illustrate one team's practices rather than establish general productivity or safety results.

This summary is based on the video's English auto-generated captions, not an independent original-audio review. Product behavior and model preferences describe Ball's October 2026 account.

## Main takeaways

- **Describe the outcome, then make the surrounding work accessible.** Ball argues that stronger models let him request a faster interpreter or a small chat interface without specifying individual files and classes. But this depends on the agent, codebase, and development process fitting together: the agent needs ways to build, release, inspect CI, and investigate production behavior, not merely edit source files. [02:05–05:09](https://www.youtube.com/watch?v=Z7l1EHfCMU8&t=125s), [05:09–06:13](https://www.youtube.com/watch?v=Z7l1EHfCMU8&t=309s)
- **Batch alternatives instead of supervising every turn.** He lets agents work while he does something else, then reviews their results on his own schedule. For visual iteration, he asks for several candidate fixes and a page or screenshots that make them comparable. An icon-alignment example shows why: he could choose the best result more easily than specify its exact geometry beforehand. He acknowledges that some work, such as infrastructure changes, still needs back-and-forth. [11:01–13:43](https://www.youtube.com/watch?v=Z7l1EHfCMU8&t=661s)
- **Ask for evidence before reviewing the critical code.** His recurring request is “give me irrefutable proof that this works”: exercise the real system, produce a test matrix, capture demonstrations, and show logs or performance measurements. These artifacts change what he looks for in review: whether the approach is right, whether he understands it, whether it has bugs, and whether he can change it later. He distinguishes central, high-impact code such as database migrations from lower-risk UI details. “Irrefutable” is his prompt wording, not a guarantee that tests prove the absence of defects. [13:43–15:39](https://www.youtube.com/watch?v=Z7l1EHfCMU8&t=823s)
- **Let measurements challenge the proposed fix.** In a thread-search performance example, he asks the agent to reproduce the issue on a large thread and profile it end to end. The investigation rejects the initial diagnosis, changes something else, and reports comparative timings. The useful deliverable is an observed improvement, not merely implementation of the first suggested optimization. [16:42–17:44](https://www.youtube.com/watch?v=Z7l1EHfCMU8&t=1002s), [17:44–18:47](https://www.youtube.com/watch?v=Z7l1EHfCMU8&t=1064s)
- **Document tools and access, not only prescribed workflows.** Repository instructions and skills explain how to start services, seed data, query systems, and inspect production. Ball says access can be read-only according to risk. Searchable past agent threads add the reasons behind earlier changes, while shared environment setup lets a teammate's new verification capability benefit everyone. He distinguishes isolated, per-thread remote machines called orbs from runners on shared machines, and describes delegating macOS-specific checks to a runner. [18:47–20:45](https://www.youtube.com/watch?v=Z7l1EHfCMU8&t=1127s), [21:48–24:56](https://www.youtube.com/watch?v=Z7l1EHfCMU8&t=1308s)
- **Close the loop after a change ships.** Scheduled follow-ups check whether rollout errors decrease or regressions appear; one example ends in a revert despite no increase in inference errors. Bug-report diagnostics and plugins connect investigation, fixes, release status, system-health checks, and customer communication. These are integrations the Amp team built, not capabilities a model acquires simply by seeing the repository. [09:11–11:52](https://www.youtube.com/watch?v=Z7l1EHfCMU8&t=551s), [25:58–29:05](https://www.youtube.com/watch?v=Z7l1EHfCMU8&t=1558s)
- **Evaluate whether agents actually discover the instructions.** After changing an `AGENTS.md` file, Ball asks for fresh agent environments to try representative requests and check whether they use the intended tool or script. He describes comparisons with control groups, then iterates on where instructions live. A simple starting probe is whether a fresh agent can start the development server and log him in without extra guidance. [29:05–31:11](https://www.youtube.com/watch?v=Z7l1EHfCMU8&t=1745s)

## Case study: a memory warning tested behind a feature flag

A report about orbs running out of memory starts an investigation through Slack. The agent gathers diagnostics, logs, related reports, and previous threads; Ball then questions the proposed fix rather than accepting the first implementation. The eventual change is placed behind a feature flag and deployed. With human approval for the flag, agents create memory-pressure scenarios so Ball can inspect the warning and stop controls. He reports that the feature initially affects only him and personally confirms it works. [30:08–34:07](https://www.youtube.com/watch?v=Z7l1EHfCMU8&t=1808s)

Ball argues that cheaper setup and testing make small, feature-flagged production changes more practical. His example depends on explicit access, restricted exposure, reproducible failure cases, and human checks; it is not evidence that arbitrary production testing is safe. [32:13–34:31](https://www.youtube.com/watch?v=Z7l1EHfCMU8&t=1933s)

## Limits of the advice

Ball favors the strongest available model for open-ended engineering, while allowing cheaper models for predefined workloads that meet evaluations. He also argues against manual context micromanagement. These are personal judgments about current tradeoffs, not benchmark comparisons. His team's direct-to-main, no-PR practice is described alongside senior engineers, feature flags, dogfooding, and fast fixes; the talk does not demonstrate that removing review gates suits other organizations.
