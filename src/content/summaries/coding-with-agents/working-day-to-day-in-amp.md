Thorsten from the Amp team records his ordinary work across several parallel Amp threads. Each thread carries one change from investigation through review, rollout, and follow-up. The examples include a production performance fix, a user's bug report, a UI fix, a feature promotion, and a large refactor. In each one he steers the agent, asks for evidence, and has it monitor the result after shipping.

This summary is based on the English auto-generated captions, with names and product terms corrected in the saved transcript. The speaker introduces himself only as Thorsten from Amp, and the video is published by Amp, Inc. It is an unedited vendor demonstration of internal work. Product features, internal tools, and performance numbers are first-party claims shown on screen, not independently verified results.

### Key points

- **A long-running thread follows a performance fix into production.** Thorsten's thread had shipped performance improvements and then used scheduled automations to wake itself up and check the results. Its orb, the isolated environment where the thread runs, can read production logs through Google Cloud access that the team grants and revokes per orb. The agent also used "canaries," real agent threads running in production that he had shipped the day before for debugging. While checking results, it noticed a few active threads that still dominated the slow measurements and offered to investigate them separately, which he accepted. [00:00–02:06](https://www.youtube.com/watch?v=0WeQLAZVJ8w&t=0s)
- **He asks how the fix works before sharing the numbers.** The agent explains that the improved lookup runs at least twice on every tick of the agent loop, meaning every tool run or inference call, which is why the fix affected the whole fleet. It reports a 44% drop in slow ticks across the fleet and produces a before-and-after table for Slack. The table excludes the hot-looping threads, which need a separate fix. These are internal measurements shown in the demo. [09:00–12:04](https://www.youtube.com/watch?v=0WeQLAZVJ8w&t=540s)
- **Production access requires an explicit human approval.** When the follow-up thread needs production access, it gives Thorsten a command to run. He runs it in his own terminal to approve the access, then the approval is sent back to the thread with `amp threads continue`. The thread then pulls logs, and Thorsten reads its findings as pointing to an expensive query that runs every time a tool reports progress. [11:08–12:54](https://www.youtube.com/watch?v=0WeQLAZVJ8w&t=668s), [14:50–16:54](https://www.youtube.com/watch?v=0WeQLAZVJ8w&t=890s)
- **A bug fix is checked for changed behavior and then proved with a reproduction.** A user on Nix with Home Manager reported that `amp clone` failed because Amp could not write its credential helper to the global Git configuration. The agent's first summary left it unclear whether it had only improved the error message, so Thorsten asked whether the behavior had changed. It had: Amp now treats the global setup as best effort and passes its credential helper directly to the clone command, so cloning continues with a warning. He then asked for "irrefutable proof" with a screenshot, which he compares to asking a pull-request author to show they ran the change. The agent reproduced the permission error with a setup based on the user's report, built the CLI, ran the real command, and rendered the terminal output as a screenshot. - **The same thread carries the fix through release and customer follow-up.** After reviewing the proof, Thorsten tells the agent to commit, push to main, cut a CLI release, wait until it is out, email the user, and close the bug report. He says the Amp repository has tools for emailing users and closing bug reports, and that its bug-report lookup is an Amp plugin. [22:51–23:50](https://www.youtube.com/watch?v=0WeQLAZVJ8w&t=1371s), [23:50–24:53](https://www.youtube.com/watch?v=0WeQLAZVJ8w&t=1430s)
- **A UI fix is tested in a preview before shipping.** Hover states in an experimental Puck sidebar flickered, so he recorded a screen video and sent it to the agent. The agent first blamed the archive button removing the row highlight; Thorsten pointed out that tooltips were also part of the problem, and the agent added a hover delay. Because the change was front-end only, he asked for Storybook in a portal instead of shipping it behind the feature flag and checking production. The portal loaded slowly because the Vite dev server is not optimized for remote access, but the delay fixed the flicker. [04:04–06:11](https://www.youtube.com/watch?v=0WeQLAZVJ8w&t=244s), [07:05–09:00](https://www.youtube.com/watch?v=0WeQLAZVJ8w&t=425s)
- **Shipping and rollout checks are encoded for the agent.** A ship button in Amp's changes tab gives the agent instructions to run the tests, rebase onto `origin/main`, and push to main. Thorsten then asks it to check the rollout every 15 minutes and report when the change is live. The codebase or its `AGENTS.md` file tells the agent how to confirm that: compare the server commit from a version endpoint, check CI, and check the deployment. He reloads the app at the end and confirms that the flicker is gone. - **He picks the agent mode by the kind of change.** To promote a "recap" feature from a feature-flag rollout to a user-controlled experimental setting, he uses Amp's `high` mode. He says he has been enjoying Fable 5.1 but does not need its creativity for a mechanical change, and that there is "no big science" behind the choice. His dictated prompt asks the agent to find the flag, learn how experimental settings work, promote the feature, and add explanatory text that mentions cost. When the result says the feature "may incur additional costs," he asks for a less alarming label that explains the extra inference requests. [05:06–08:04](https://www.youtube.com/watch?v=0WeQLAZVJ8w&t=306s), [12:54–13:45](https://www.youtube.com/watch?v=0WeQLAZVJ8w&t=774s)
- **The agent gathers team feedback before the feature is promoted.** Using the Slack MCP, which he says was not yet available to all users, the agent posts a question about the recap feature in the team's channel. One colleague likes it and asks for the recap to disappear when a new message is sent; another does not see what it adds beyond the last agent message. Thorsten has the agent reply that the recap already disappears for him and ask for a video of a case where it does not. The demo ends before a decision. [16:54–18:49](https://www.youtube.com/watch?v=0WeQLAZVJ8w&t=1014s), [22:51–24:53](https://www.youtube.com/watch?v=0WeQLAZVJ8w&t=1371s)
- **A large refactor is kept mechanical, tested, and still reviewed by hand.** Amp's runner node could start threads in only one directory because code throughout the CLI read the process's current working directory. Thorsten instructed the agent to make only the mechanical change of passing the directory in explicitly, adding the capability before any user-facing feature. The agent rebuilt and ran each entry point against the development stack with MCP servers, skills, and `AGENTS.md` loaded; one failure was an orb-specific access-token issue. He says he would still spot-check the most important files, consider other risks and tests, and possibly ship to a branch and test locally first. ### Limits

The video shows one engineer's day on Amp's own codebase, with access to internal tools, production telemetry, and colleagues who can review in Slack. It demonstrates a workflow rather than measuring its speed, cost, or error rate. The agent's diagnoses and reproduction are shown only as far as the screen recording goes; for example, the cause of the hot-looping threads is still under investigation when the video ends. [How Thorsten Ball Uses Amp, October 2026](/summaries/coding-with-agents/how-thorsten-ball-uses-amp-october-2026) covers many of the same practices in a longer, structured walkthrough.
