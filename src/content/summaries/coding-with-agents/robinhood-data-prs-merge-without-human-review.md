Chetas Joshi describes the reviewer Robinhood's data platform team built for pull requests to production data pipelines. Deterministic scripts check facts against live systems, an agent reviews the code for risks those checks cannot see, and people keep specific decisions the agent is never allowed to approve. He follows one schema change through the system, then explains the feedback loop, error measures, results, and design flaws.

This summary is based on the English auto-generated captions, which render the speaker's spoken name as "Jas"; the video title identifies him as Chetas Joshi of Robinhood. He describes himself as an engineer on the data platform team who builds the data ingestion and processing frameworks behind the company's data lake. All results are Robinhood's own reported figures.

### Key points

- **Passing CI does not show that a data change is safe.** Joshi's examples of what green CI can miss are a broken freshness service-level agreement (SLA), a consumer on another team that breaks, and newly exposed data. AI coding assistants made pull requests for queries, schema changes, pipeline code, configuration, and access grants cheap to open. The number of people who know who reads a table, how large it is, and how sensitive its data is did not grow, so review queued in front of them. [00:00–03:58](https://www.youtube.com/watch?v=MQiojLnK-E0&t=0s)
- **Scripts check facts; the agent judges what needs context.** Layer 1 is deterministic scripts that query a source of truth. A failure turns CI red and blocks the pull request, with no model involved. Layer 2 is an agent whose rules list what layer 1 already checks, so it looks for other risks. Both layers review the same pull request, and merging requires passing checks plus an approving review. Joshi also presents this split as a cost control: AI is not used to rediscover facts a script can look up. [03:58–04:50](https://www.youtube.com/watch?v=MQiojLnK-E0&t=238s)
- **Layer 1 has four checks, each limited by its records.** Data contracts compare a changed schema and keys with the schema registry. Required tags confirm in the catalog that each table has an owner and that any personal data (PII) is labeled. The lineage blast-radius check walks every downstream job recorded in the lineage tool for a changed column. A performance test runs the change in staging at production data volume with mock data to check cluster sizing and the freshness SLA. Joshi stresses that the lineage check is only as complete as the lineage record. [06:49–09:46](https://www.youtube.com/watch?v=MQiojLnK-E0&t=409s)
- **The agent reads the repository, not live systems.** It starts from the diff and treats the pull request description as intent that cannot override a finding in the code. Its tools can read, search, and list repository files, so it can follow a change into pipeline definitions and access grants. It cannot query the catalog, lineage tool, or production state. Its rules vary by change type and target three risks: query anti-patterns, such as an unpartitioned cross join that works but overloads a cluster; grants that open sensitive data; and consumers missing from lineage. [09:46–12:34](https://www.youtube.com/watch?v=MQiojLnK-E0&t=586s)
- **The worked example: a type widening that broke an unregistered job.** The pull request added a column from an upstream source and widened an existing column from integer to big integer. [04:50–06:49](https://www.youtube.com/watch?v=MQiojLnK-E0&t=290s) Every layer 1 check passed. [08:50–10:46](https://www.youtube.com/watch?v=MQiojLnK-E0&t=530s) The agent found a job in the repository that read the widened column and wrote it into another table where the column was still an integer, so the first value too large for an integer would make that write fail. The job was missing from lineage because workloads run on several query engines and each engine must publish its own lineage. [11:39–13:36](https://www.youtube.com/watch?v=MQiojLnK-E0&t=699s)
- **A person confirmed the risk, and the fix changed the merge order.** The agent scored the risk high and escalated with the full chain in its review comment. A human reviewer checked that the job was live in production, which the agent could not see. The change was not rejected: the downstream table was updated first, then the pull request merged, and Joshi reports no incident. [15:33–17:30](https://www.youtube.com/watch?v=MQiojLnK-E0&t=933s)
- **The agent may report only what it searched.** Ad hoc queries and dashboards live outside the repository, so a code search cannot find them. If the agent finds no downstream consumers, it must say it found none in the places it searched, not that none exist. [13:36–14:36](https://www.youtube.com/watch?v=MQiojLnK-E0&t=816s)
- **Each review has line comments, a risk score, and a decision.** Comments explain why a specific line matters, such as which job reads a changed column. The risk score decides whether the agent approves or escalates, and an escalation carries the comments to the human reviewer. [14:36–15:33](https://www.youtube.com/watch?v=MQiojLnK-E0&t=876s)
- **Some changes always go to a person.** The agent can approve most changes when checks pass and it is confident. It can never approve grants that touch sensitive data, migrations that change what data means rather than how it is moved or stored, or cases where it is not confident in its own verdict. In those cases it only reports the risk and its reasoning. [16:38–17:30](https://www.youtube.com/watch?v=MQiojLnK-E0&t=998s), [17:30–18:19](https://www.youtube.com/watch?v=MQiojLnK-E0&t=1050s)
- **Rules improve through a manual weekly pass.** People reply to the agent's verdict, agreeing or disagreeing and explaining why. Replies are collected daily, and once a week the on-call engineer edits the review rules by hand; nothing retrains automatically. In one example, the agent flagged a pull request that labeled a column nonsensitive in the lake although its source marked it as PII. The author pointed to how similar columns were classified, and a human agreed because the ingestion pipeline encrypts that column before writing it. Joshi cautions that this depends on that pipeline and is not a general rule that encryption makes data nonsensitive. An agent to help with the weekly pass is an idea, not built. [17:30–20:02](https://www.youtube.com/watch?v=MQiojLnK-E0&t=1050s), [20:02–20:56](https://www.youtube.com/watch?v=MQiojLnK-E0&t=1202s)
- **Measure both misses and false escalations.** A miss is a bad pull request the agent approved; a false escalation sends a fine one to a person. Joshi argues that a reviewer that escalates everything avoids misses without reducing review work. He reports a miss rate of about 2% as of August 31, 2026, mostly from gaps in the rules rather than failures of judgment. He has no clean false-escalation figure, but says their main cause is missing context, as in the encrypted-column example. In one miss, columns retagged as PII moved from an open copy of the data to a restricted one, and a downstream reader of the open copy broke. The new rule searches the codebase for readers of a column before it is retagged as sensitive. [20:02–22:42](https://www.youtube.com/watch?v=MQiojLnK-E0&t=1202s)

### Reported results

As of August 31, 2026, Joshi reports that about 60% of data pipeline pull requests merged without human review, manual review effort fell about 75%, the time saved is about 132 engineering hours a month, and incidents tied to these pull requests fell about 30%. He says protected decisions still reach a person by design. The talk does not give the baseline period, pull request volume, or how effort and incidents were measured. [22:42–24:35](https://www.youtube.com/watch?v=MQiojLnK-E0&t=1362s)

### Current design flaws and a proposal

The two layers are separate systems that run in parallel, and neither sees the other's pass, fail, or outage state. The agent knows what the scripts are configured to cover, not what happened when they ran, and it cannot call them to fetch a live fact. When one side cannot finish, the pull request waits for a human; there is no automatic fallback. The platform team is exploring a single entry point: a classifier would decide which parts of a pull request to review separately or together, and the agent would get the layer 1 checks as callable tools. Joshi labels this a proposal that is not built. [23:32–26:34](https://www.youtube.com/watch?v=MQiojLnK-E0&t=1412s)

### Lessons

Joshi closes with three lessons: let scripts prove anything a source of truth can prove, because that is cheaper and needs no AI; never let the agent clear sensitive grants, migrations that change intent, or low-confidence verdicts; and count false escalations as carefully as misses. [25:39–28:00](https://www.youtube.com/watch?v=MQiojLnK-E0&t=1539s)

### Limits

The results are first-party figures from one team's data pipelines, not all Robinhood code. The talk does not name the model, explain how the risk score or the agent's confidence is calibrated, or define the denominator for the miss rate.
