Sonar's Manish Kapur and Anthropic's Addy Osmani discuss how teams can merge more agent-written code without merging it blind. Their shared answer is verification: agents should produce tests and other evidence that a change works, and teams should add automated checks at every stage before they give agents more autonomy.

This summary is based on the English auto-generated captions. The talk is a moderated conversation. Kapur, who leads product and solution developer relations at Sonar, asks questions and presents survey figures and Sonar's verification approach. Osmani, who says he works on the Claude Code developer experience, describes Anthropic's practice. Anthropic's workflow and merge counts are first-party accounts, and Sonar's layered approach is a vendor recommendation. The title's 30,000 daily changes come from an Anthropic post that Kapur cites. Osmani gives only the earlier figure of about 2,500 changes in May and does not explain how Anthropic reached the larger number.

### Key points

- **A software factory runs agent loops at scale, with more or less human involvement.** Osmani describes a "lights-on" factory as one where agents repeatedly plan, build, check, and ship code while people still apply judgment within the loop. In a "dark" factory, people mostly define intent and step in only for exceptions. He places most teams between the two. In his account, the amount of trustworthy verification determines how far a team can move toward the dark end. Kapur compares the factory to an assembly line that automates each development step. [02:48–03:38](https://www.youtube.com/watch?v=AnsXWH2_EBU&t=168s), [10:29–11:22](https://www.youtube.com/watch?v=AnsXWH2_EBU&t=629s)
- **Give agents a way to check their own work.** Osmani says agents can now generate checks such as tests, benchmarks, and specs much more cheaply than before, and that teams should spend their time refining these checks. He argues that an agent that can show its work is correct and complete produces far better results, and he says this can improve outcomes two- to threefold. He gives no measurement behind that figure. [03:38–05:34](https://www.youtube.com/watch?v=AnsXWH2_EBU&t=218s)
- **At Anthropic, Claude reviews first, and people check the evidence.** Osmani says Anthropic was merging about 2,500 changes in May, which Kapur presents as a daily figure, and that a recent Claude.ai refresh involved about 3,000 pull requests merged in a short period. His description of the review workflow has four parts:
  1. Claude does a first-pass review. It needs a way to use the change as a user would, such as running end-to-end tasks, checking the result in a browser, running tools, and linting.
  2. Hooks run on every edit and examine the diffs, so problems found during review are corrected in the pull request quickly.
  3. Teams write their best practices and preferences into shared `CLAUDE.md` or `AGENTS.md` files, which the agent consults during review.
  4. People review the agent's evidence. For browser UI, that can be a video of the agent clicking through the feature, or screenshots of the mobile and desktop layouts.

  Osmani also mentions Anthropic's code review product, which the team uses internally. He does not describe how often people inspect the code itself or how often the process misses defects. [05:34–08:37](https://www.youtube.com/watch?v=AnsXWH2_EBU&t=334s)
- **Say which tests count as verification.** Osmani argues that telling people to "verify the work" is too vague. Anthropic relies on end-to-end tests, property tests, and visual verification to gain enough confidence to merge changes automatically. He expects further gains from both verification and model quality, but considers current models already good and says shared verification practice is becoming more important. His advice for leaders is to compare their current testing with what they would need before letting agents approve merges. Junior developers should gain experience with these kinds of tests. [08:37–10:29](https://www.youtube.com/watch?v=AnsXWH2_EBU&t=517s), [16:51–17:39](https://www.youtube.com/watch?v=AnsXWH2_EBU&t=1011s)
- **Sonar recommends separate verification layers for different kinds of problems.** Kapur says Sonar wants verification in every loop (the agent's own loop, the CI loop, and code maintenance) and describes three layers. A deterministic layer catches bugs and security issues such as SQL injection and buffer overflows. An agentic review layer looks for logic and intent errors that rule-based analysis is not suited to find. A supply-chain layer checks dependencies for CVEs, malware, and malicious packages. This is Sonar's recommended approach. The talk gives no evidence of how well each layer performs. [11:22–13:12](https://www.youtube.com/watch?v=AnsXWH2_EBU&t=682s)
- **Governance concerns center on control, permissions, and sandboxes.** Osmani says companies that let teams experiment freely found themselves with hundreds or thousands of agents touching systems and data, and possibly deploying to production, without knowing what those agents were doing. Enterprises now ask about agent identity and telemetry, and about keeping agents inside their sandbox. Kapur calls Sonar's version of these controls "guide rails." [13:12–14:55](https://www.youtube.com/watch?v=AnsXWH2_EBU&t=792s)
- **Label agent-written pull requests, but keep a human owner.** Osmani personally favors labeling. He says Anthropic does not mind Claude being credited as the author because the team focuses on what ships to users. A label also helps reviewers decide which extra checks an agent-written change needs. The person who started the agent run still owns the change and must fix it if it breaks. Kapur suggests labeling for at least the next six to nine months, until teams trust their factories, and points to auditability needs in financial services. [14:55–16:51](https://www.youtube.com/watch?v=AnsXWH2_EBU&t=895s)

### Limits

Most figures are slide statistics read aloud without method details. Kapur cites a CircleCI analysis of 28 million CI workflows: throughput rose about 59%, while three in ten attempts to merge into production failed [01:56–02:48](https://www.youtube.com/watch?v=AnsXWH2_EBU&t=116s). He gives adoption and verification percentages without naming their source [03:38–04:41](https://www.youtube.com/watch?v=AnsXWH2_EBU&t=218s). He attributes later figures to Sonar's forthcoming State of Code survey of more than 1,000 developers, which was not yet published. One of them, about how much code reaches production without review, is unclear in the captions [07:40–10:29](https://www.youtube.com/watch?v=AnsXWH2_EBU&t=460s). His figures for companies with approved agents and shared controls, and for those running factories autonomously, also come without a method [13:12–14:05](https://www.youtube.com/watch?v=AnsXWH2_EBU&t=792s). The predictions are forecasts. Osmani expects mostly light factories "with some dark corners" by the end of 2027, and Kapur guesses that Anthropic will run a dark factory this year or next [14:55–15:59](https://www.youtube.com/watch?v=AnsXWH2_EBU&t=895s). Osmani's merge criterion is general: an agent's pull request is safe to merge when you are fully confident nothing will go wrong, or have reduced that risk as far as possible [16:51–17:39](https://www.youtube.com/watch?v=AnsXWH2_EBU&t=1011s).
