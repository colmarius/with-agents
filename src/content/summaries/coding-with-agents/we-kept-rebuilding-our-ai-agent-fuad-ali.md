Fuad Ali describes two years of rebuilding Alyx, the agent inside Arize's AX platform that reads traces, builds evaluations and datasets, and runs multi-step tasks for users. Arize did not train models, so every rebuild changed the harness: the code around the model that keeps the plan, decides when a turn ends, and manages context and memory. The talk explains which harness decisions Arize reversed and which ones lasted.

This summary is based on the English auto-generated captions, with the product names Alyx, Arize AX, and Signal corrected in the transcript against Arize's documentation. Ali works on product at Arize as an AI product manager. Everything in the talk is a first-party account of Arize's own agent, and the descriptions of Arize tracing, experiments, and its Signal trace-review agent are vendor claims. Ali reports design outcomes, such as a simple memory file working better than more complex stores, without showing the evaluations behind them.

### Key points

- **The harness changed more than the model.** Arize began with a late-2023 prototype on 3.5-era models. A staff engineer recalls it as about half hallucination. The team soon moved math out of the model and into harness code. The first launched version, then called a copilot, routed requests through a decision tree to a set of skills. An August 2025 rewrite added iterative tool calling and a to-do tool. Alyx 2.0 followed in February 2026 with Sonnet 4.5 as the default model. A June release merged the specialist agents into one agent, and long-term memory came later. Arize uses no agent framework; the loop, plan, stopping rule, and memory are its own code. [02:48–05:39](https://www.youtube.com/watch?v=YIhvrvHtonk&t=168s), [05:39–06:38](https://www.youtube.com/watch?v=YIhvrvHtonk&t=339s)
- **Move the plan out of the model and into the harness.** When Alyx had a to-do tool, the model spent most of its time updating the list. Many model calls did no useful work beyond checking off items, and the agent lost focus after many tool calls. Arize moved the plan into the harness in steps:
  1. It added an "in progress" marker so the model would not lose its place.
  2. It rendered the plan into the messages on every model call, so the plan's rules appeared next to the current data.
  3. It dropped the "in progress" marker, because the first unfinished item in the ordered list already identifies the next task.
  4. It is now testing a version with no to-do tool, where the harness keeps the plan state and checks completion, and the model only reads the plan and does the next item.

  Ali's lesson is that models can be "very eager" with lists. [06:38–08:32](https://www.youtube.com/watch?v=YIhvrvHtonk&t=398s)
- **The harness, not the model's text, decides when a turn ends.** Arize first treated a response with text and no tool calls as finished. That broke on models that announce a step in one response and make the tool call in the next. Because AX customers can choose their own model provider, Arize cannot test every model a customer might use, so it designs the harness to tolerate different model behaviors and runs regression benchmarks across models. Alyx now has to call an explicit finish tool. The harness rejects that call, up to three times, while plan items remain open. It warns the model one step before the iteration limit and can force a finish. [08:32–10:14](https://www.youtube.com/watch?v=YIhvrvHtonk&t=512s)
- **Store large results outside the context and keep a pointer.** Traces from other agents can include JSON large enough to fill the context window and leave room for no useful work. Alyx stores such a result, truncates it inside the context, and keeps a reference to it. If the agent needs the full content, it writes code, for example with `jq`, to query the stored result. Ali compares this to keeping a sticky note on your desk that says which shelf a book is on. When the agent's own history grows past a set token budget, the harness has the model write a checkpoint and then drops the messages the checkpoint replaces. [09:24–12:08](https://www.youtube.com/watch?v=YIhvrvHtonk&t=564s)
- **A small file per user is the long-term memory.** Arize tried vector retrieval, episodic and semantic stores, and temporal knowledge graphs. It settled on one Markdown file per user, capped at 8,000 characters. The file is loaded on every request and updated by a background job after each session ends. Ali gives these reasons for the choice: the file is small and exact, it does not fill the context, people can review it and adjust the background job's instructions, and a single writer at the end of a session is easier to secure against writing one user's information into another user's file. He presents this as a lesson about over-engineering and does not report how the alternatives compared. [11:16–13:53](https://www.youtube.com/watch?v=YIhvrvHtonk&t=676s)
- **One agent with on-demand skills replaced page-specific specialists.** In 2025, Alyx had one agent that did trace analysis, then grew to ten specialists, one for each product page. A dataset page, for example, had a sub-agent for synthetic data. Arize merged them back into one agent that loads skill instructions and tools when it needs them and chooses which tools to use. Ali credits both better models and simplification. [12:58–14:56](https://www.youtube.com/watch?v=YIhvrvHtonk&t=778s)
- **Choose the fast model that is good enough.** Arize does not switch its default to the newest model automatically, because the best model on general benchmarks may not be best for a specific product. It defaults to a model that is fast and good enough, and spends the effort on the harness. It is starting to explore per-task model routing and small post-trained models for narrow tasks. Some features need only a single model call rather than an agent loop; Ali's example is generating trace filters from natural language. [13:53–15:43](https://www.youtube.com/watch?v=YIhvrvHtonk&t=833s)
- **Production sessions become test cases.** Arize traces every Alyx session and turns production traces into regression datasets that grow as new failures appear. A whole session can be saved as a dataset and a specific turn replayed through the agent. The team uses Arize experiments to compare harness changes. [14:56–16:33](https://www.youtube.com/watch?v=YIhvrvHtonk&t=896s)
- **Agent bugs often look like successful runs.** Ali says agent bugs rarely appear as explicit errors. A run can report an OK status while making 43 identical tool calls in one turn. A 227-second response is clearly too slow, but the acceptable latency depends on the use case. Arize now uses Signal, its agent that reads Alyx's traces, to find such patterns, including retry loops, so staff engineers read fewer traces by hand. The talk names these examples but does not explain their causes or fixes. [01:45–02:48](https://www.youtube.com/watch?v=YIhvrvHtonk&t=105s), [16:33–17:24](https://www.youtube.com/watch?v=YIhvrvHtonk&t=993s)
- **People still set the baseline and make tradeoffs.** Arize aligns its LLM judges against gold labels and golden datasets created by people. Ali says the tradeoff between speed and quality remains a human decision even when metrics show how a model change would affect latency and response quality. [17:24–18:26](https://www.youtube.com/watch?v=YIhvrvHtonk&t=1044s)
- **Six practices survived the rebuilds.** Ali lists tracing everything Alyx does; keeping math and data work in code, so code computes aggregations and the model reasons about and explains the results through tools; golden datasets in CI; errors with an obvious fix; streaming and persistence; and skills, which he defines as giving the model a capability around an external system. He does not expand on the error, streaming, or persistence items. [18:26–19:22](https://www.youtube.com/watch?v=YIhvrvHtonk&t=1106s)
