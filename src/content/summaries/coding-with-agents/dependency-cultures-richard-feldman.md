Richard Feldman argues that the number of dependencies a project uses depends mostly on its ecosystem's habits, not on what the project technically requires. He compares projects that do the same job, shows how dependency count and automatic updates create supply-chain exposure, and describes alternatives to adding a package: trimming one, copying a small piece, or writing the code yourself.

This summary is based on the English auto-generated captions. Feldman works on the Roc programming language and uses the Roc website as his main example. The dependency counts are his own unlabelled comparisons, and he calls them "not perfect science". Views attributed to Jonathan Blow and Mitchell Hashimoto are his paraphrases and quoted slides, not their own statements in this talk. The talk is about software dependencies in general. Its only coding-agent material is a short example of using a language model to port code.

### Key points

- **Similar projects can have very different dependency counts.** Feldman compares the websites of eight programming languages, all static sites with documentation, examples, and syntax highlighting. The TypeScript site has almost 1,800 dependencies, almost all indirect (dependencies of dependencies), while the Roc site has none. Both sites compile code in the browser, but the TypeScript compiler is a small part of that count. Feldman traces most of it to Gatsby, which brings in about 1,500 indirect dependencies. [03:56–06:32](https://www.youtube.com/watch?v=E82ly38YEEQ&t=236s)
- **Package-manager lineage matches the patterns, which he reads as culture.** TypeScript and Node.js share npm. Ruby and Rust show a similar shape, and he notes that Rust's package manager was built with help from people who built Ruby's Bundler. Zig and Roc, which uses Zig's package manager, have almost no dependencies. Python and Go each show their own pattern. From these groupings he claims dependency counts are cultural norms, not technical necessity. [06:32–08:13](https://www.youtube.com/watch?v=E82ly38YEEQ&t=392s), [08:13–09:15](https://www.youtube.com/watch?v=E82ly38YEEQ&t=493s)
- **Game development shows the same spread.** Feldman compares nine open-source or source-available games written in Rust, C#, and C++. Two remakes of the same game have 29 and 30 direct dependencies but very different numbers of indirect ones. The C++ games have very few direct dependencies and no indirect ones. In that culture, developers usually vendor dependencies, which means they copy the dependency's source into their own repository. [09:15–12:55](https://www.youtube.com/watch?v=E82ly38YEEQ&t=555s)
- **Checking dependencies into the repository removes some failure modes.** Feldman reports Jonathan Blow's view, from the Software Unscripted podcast, that external code should live in a folder you check in. The project then builds without network access, and an older checkout already contains the dependency versions it used. Feldman says this is unreasonable with 1,800 packages but sensible with a few. He uses left-pad as the counterexample: a one-function package whose removal from npm broke many builds, which also showed that many projects did not cache their dependencies. [12:04–14:50](https://www.youtube.com/watch?v=E82ly38YEEQ&t=724s)
- **Update policies range from "always" to "only when needed".** Feldman describes npm culture as updating constantly and C++ game development as rarely updating. Go's module system takes a middle position: it selects the minimum version that satisfies the requirements, and upgrades happen only when a developer asks for them. At the extreme, Mitchell Hashimoto trims dependencies down to the parts he uses and updates only to fix a problem users hit. Hashimoto argues that latent bugs can be tracked through CVEs (published vulnerability records). Updating, by contrast, would require reviewing every commit in the full set of direct and indirect dependencies. [15:39–19:23](https://www.youtube.com/watch?v=E82ly38YEEQ&t=939s)
- **HashiCorp is an existence proof, not a guarantee.** Hashimoto asked engineers who wanted an update to show the commit they needed. Feldman cites HashiCorp's growth to a public company as evidence that this slower practice does not prevent business success. He adds that the example does not guarantee the same result for others. [19:23–20:40](https://www.youtube.com/watch?v=E82ly38YEEQ&t=1163s)
- **A tiny dependency became a malware path.** In a 2014 issue, a user asked the event-stream library for a four-line `flatMap` function. The maintainer asked for it to be published as a separate module and added that module as a dependency. A later patch release of the module added code that tried to steal cryptocurrency. Feldman's verdict is that four lines did not justify a dependency. Copying them, with attention to licensing, or doing without them would have avoided the indirect dependency. [20:19–22:18](https://www.youtube.com/watch?v=E82ly38YEEQ&t=1219s), [22:18–23:07](https://www.youtube.com/watch?v=E82ly38YEEQ&t=1338s)
- **Automatic updates trade latent bugs for new risks.** Feldman criticizes Dependabot's claim that keeping dependencies updated is an easy way to stay secure. He agrees updates are double-edged: they can fix bugs and improve performance, but they can also add bugs, bloat, or malware. Log4Shell shows the other side. Once a fix existed, users needed it quickly, but projects whose indirect dependencies had not updated stayed exposed. His conclusion is that fewer indirect dependencies help with both risks. [23:07–24:57](https://www.youtube.com/watch?v=E82ly38YEEQ&t=1387s), [25:48–27:26](https://www.youtube.com/watch?v=E82ly38YEEQ&t=1548s)
- **Feldman cites a sharp rise in malicious packages.** He says about half a million malicious packages were found in 2024. That is 1.5 times the 2023 figure and more than 1,000% above 2020. He does not name the source of these figures in the talk. He uses them to argue that malicious updates are now a larger risk than latent bugs like Log4Shell. He also asks library authors to consider the indirect dependencies they impose on users. [27:26–28:22](https://www.youtube.com/watch?v=E82ly38YEEQ&t=1646s), [28:22–29:22](https://www.youtube.com/watch?v=E82ly38YEEQ&t=1702s)
- **The Roc syntax highlighter shows the alternative in practice.** Searching npm moved his attention from the problem to choosing a package. highlight.js offers 192 languages and 512 themes, but Roc needs one language, and custom languages are defined with regular expressions. Roc allows string interpolation nested to any depth, which regular expressions cannot represent correctly. Feldman instead ported the compiler's Zig tokenizer to JavaScript. He reports spending under an hour asking a language model to translate it, then iterating because the first result was imperfect. The result is about 1,000 lines to maintain and 6 KB, compared with roughly 9 KB compressed for highlight.js before adding any languages. It handles Roc's edge cases and can mirror tokenizer changes line for line. His claim that it runs faster is not measured in the talk. [28:22–34:06](https://www.youtube.com/watch?v=E82ly38YEEQ&t=1702s), [34:06–34:56](https://www.youtube.com/watch?v=E82ly38YEEQ&t=2046s)
- **The choice is a spectrum, not "no dependencies".** Feldman says pulling a package off the shelf is often correct. Between that and writing code yourself, you can fork a package and remove parts, or copy code with attribution. The Roc compiler, for example, copies MIT-licensed code from the Zig compiler with a comment. He grants that services such as AWS Lambda provide real value, but warns that the number and interconnection of dependencies becomes a cost in its own right. [34:56–36:47](https://www.youtube.com/watch?v=E82ly38YEEQ&t=2096s), [36:47–38:32](https://www.youtube.com/watch?v=E82ly38YEEQ&t=2207s)
- **Change a dependency-heavy team gradually.** For a Node.js company with gigabytes of dependencies, Feldman suggests questioning each new dependency and proposing to replace small existing ones with a few lines of code. Small wins can then build support for larger changes. [39:28–41:29](https://www.youtube.com/watch?v=E82ly38YEEQ&t=2368s)
- **A cooldown period is better than updating immediately, but it is still second-best.** Asked about waiting seven days so scanning companies can inspect a new release, Feldman calls this "less bad". His order of preference is: vet updates yourself as Hashimoto does, then delay updates until others have had time to find problems, and update immediately only as a last resort. Scanning addresses malware but not performance regressions or new bugs. He also says he lacks experience with operating-system package managers, where vetting standards such as Debian's may differ. [42:23–43:10](https://www.youtube.com/watch?v=E82ly38YEEQ&t=2543s), [43:10–44:51](https://www.youtube.com/watch?v=E82ly38YEEQ&t=2590s)

### Limits of the argument

The comparisons count dependencies for selected projects; they do not measure security incidents, maintenance cost, or developer time. Feldman's claim that the differences are mostly cultural is his interpretation of how the projects group. Vetting every commit or porting code yourself costs time, and the talk shows one small example rather than a cost comparison. The language-model port is a brief anecdote. It suggests that generating a small, well-specified replacement can be cheap, but the talk does not discuss reviewing or maintaining such generated code beyond Feldman's own iteration.
