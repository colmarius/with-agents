In this MEGA DEV livestream, Kent C. Dodds takes one small feature for his product, Kody, from a GitHub issue to a merged and deployed pull request without reading the implementation. Along the way, he explains the repository documentation, review loop, feature flags, and scheduled cleanup agents that he says let him trust this process.

This summary is based on English auto-generated captions; product and tool names were corrected in the saved transcript where the captions misspelled them. Dodds demonstrates his own product and teaches in MEGA, the paid course the stream promotes. The host spends about ten minutes on a sales pitch for the course. [1:33:13–1:44:50](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=5593s) Reliability, cost, and security outcomes are Dodds's own reports from a solo-developed product, not measured comparisons.

### Key points

- **Find the user's problem, then align an agent on it before delegating.** The feature request asks Kody to tell users when a community package they forked has changed upstream. Kody is Dodds's platform for agent-shared memory, secrets, packages, triggers, integrations, and apps. [12:04–14:58](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=724s), [16:01–18:06](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=961s) Dodds advises looking for the core problem in feedback rather than adopting the user's suggested solution. He asks a persistent planning agent to read the issue even though he has already read it, so they share the same context. It explains the gap back to him, so he can spot misunderstandings. Together they settle the scope: forked packages only, an item on Kody's "waiting" page, an event that other automations can subscribe to, and a feature flag limited to users who opted into experiments. [22:08–24:15](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=1328s), [25:18–27:14](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=1518s), [31:05–34:05](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=1865s) For less obvious features, he would first ask an agent to check production data for how many users have the problem. [36:11–37:15](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=2171s)
- **Keep product understanding human, and hand implementation to a separate agent.** Dodds argues that developers can no longer leave knowledge of users to a product manager, because agents now perform the ticket-to-implementation step. [29:07–31:05](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=1747s) After the discussion, the planning agent passes the brief to a second persistent agent, "Cole," which starts a Cursor cloud agent running Opus 5.5. Dodds says he never reads the prompt Cole gives it. [34:05–37:15](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=2045s) Separating discussion from implementation lets him start the next conversation while work runs; he says it is not unusual for him to have 12 agents running at once. He accepts that this is expensive and argues for increasing value as well as cutting cost. Each merged pull request posts a Discord summary with its cost, difficulty, and model, so he can judge whether a feature was worth it. [1:09:29–1:13:31](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=4169s)
- **Store context in the repository, not in an agent.** Because records live in the repository, Dodds says any agent can be replaced by a new one with no history. `AGENTS.md` serves as an index to other documents, and he treats each agent as a new hire who should discover only the documentation the task needs. [46:21–48:28](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=2781s), [55:29–56:33](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=3329s) A scope document records what the product will not become, such as a chat agent. Architecture decision records keep the reasons and consequences of choices. In one example, the status page runs as a separate Cloudflare worker so it survives a Kody failure; a full Cloudflare outage would still take both down, a risk he accepted. [49:29–52:20](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=2969s) Agents write and maintain these documents; he iterates on them with the agents rather than writing them himself. [1:04:24–1:05:28](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=3864s)
- **Make agents report friction instead of silently working around it.** After finishing a feature, an agent opens a friction issue describing problems such as a server that failed to start. A daily agent fixes these issues or marks them as needing a product decision. Dodds's reasoning is that agents will not complain about a broken setup, so every future agent repeats the same workaround. [47:23–49:29](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=2843s) The demo also shows the limits: several resolved issues had not been closed, and Dodds himself had to flag an 18-minute wait in the live run. [1:26:06–1:28:12](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=5166s)
- **Classify each change by the building blocks it touches.** Dodds keeps a YAML catalog of "primitives," the codebase's established building blocks. Examples include the app UI, the MCP server with only search and execute tools, sessions, OAuth, role-based access control, and entitlements, each with its code and documentation location. Every pull request includes a "system recap" in which the agent states whether it composed existing primitives, expanded one, deleted one, or created a new one. That classification feeds into whether the change counts as low, medium, or high risk. He says this steers agents toward existing mechanisms, such as the established way to send email or authenticate, instead of new ones; an agent adding a new primitive marks the change high risk. He calls primitives the biggest factor in avoiding low-quality agent output, which is his judgment. [57:37–1:04:24](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=3457s), [1:06:28–1:08:26](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=3988s)
- **Let the agent drive the pull request through checks and independent reviewers.** A "ship PR" skill tells the agent to keep the pull request as a draft while iterating, which avoids paying for CI on every commit. It then assigns a risk level, marks the pull request ready, and fixes CI failures. For medium or higher risk, it waits for Cursor Bugbot, CodeRabbit, and Devin. It must check each review comment rather than accept it verbatim, and it repeats until CI passes and the reviewers approve. [1:45:54–1:48:39](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=6354s) Each pull request also gets a preview of all of Kody's workers, with their own storage, mocked third-party services, and seeded users. The agent can use a CLI to test risky changes there. Dodds performed these steps by hand before turning them into the skill. [1:48:39–1:51:39](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=6519s) In the demo, the pull request had been iterating for 42 minutes when Dodds checked it. After CI passed and the reviewers approved, his bot merged it and GitHub Actions deployed it. [1:44:50–1:45:54](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=6290s), [1:54:46–1:55:49](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=6886s)
- **Rely on several safeguards, because tests alone are weak.** Dodds agrees with a viewer that tests written by the same agent that implemented a feature are not a strong gate. His confidence rests on AI reviewers he trusted only after using them manually for a while. Each reviewer runs in a separate context from the implementing agent; he has found self-review less useful. [1:51:39–1:54:46](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=6699s) Feature flags let him turn off a broken feature quickly. He also asks agents to judge decisions by how easily they can be reversed, and flags can make a hard-to-reverse launch easier to back out. [1:15:38–1:17:46](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=4538s) As a last resort, his database backups are stored off Cloudflare, on Fly.io, and he stresses testing restores. [52:20–55:29](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=3140s)
- **Schedule agents to remove what other agents add.** Dodds says agents rarely delete code and tend to keep fallbacks during migrations. A weekly "legacy reaper" agent removes legacy code and fallbacks. When removal is uncertain, it adds usage metrics and deletes the path later if it receives no traffic. It also reviews cleanup issues, each of which states when removal will be safe; one tracks the legacy MCP handler kept for older clients. [1:17:46–1:22:58](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=4666s) A nightly agent revises tests against his testing principles. For example, a test written to confirm that text was removed from a footer helps during implementation but is not worth keeping. Another agent checks documentation, and CI checks measures such as bundle size. [1:28:12–1:31:16](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=5292s)
- **Audit with each new model.** For security, Dodds asks each new model to audit the whole codebase for security, accessibility, architecture, and maintainability, then works through the recommendations with an agent in priority order. He reports that the audits have found few security problems and that no major security problem has reached production. That is his account, not an independent assessment. [1:31:16–1:34:16](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=5476s)
- **Delegate work, then turn repeated agent work into software.** His recurring question is whether an agent could do the current task, followed by whether the agent's work could become deterministic code. He argues that such code is cheaper, more reliable, and safer than repeated inference, and that people should do a task manually first to understand what the software must do. He wants that software usable by any agent rather than locked into one harness, which is the role he describes for Kody. [1:22:58–1:27:10](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=4978s)
- **Smaller teams are an opinion from a solo developer.** Dodds argues that teams should shrink, because each additional person adds coordination while implementation is no longer slow. He qualifies this as the view of someone who works alone and says he has no personal experience applying the process in a large team. His suggestion for larger teams is to spend meetings on product direction and how the system's primitives are changing. [43:13–46:21](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=2593s)

### Limits

The live feature is small, and the stream does not show it working for a user. Dodds enables the feature flag but does not trigger an upstream update; he asks viewers to trust that it works. [2:00:39–2:02:47](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=7239s) He credits much of the process to current models and agent harnesses, and his evidence is his own product: paying users, a codebase of more than 800,000 lines built since March 18, and model audits that he says call the architecture solid. [1:13:31–1:15:38](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=4411s), [1:53:44–1:54:46](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=6824s), [1:31:16–1:33:13](https://www.youtube.com/watch?v=3kK3rfb1BZQ&t=5476s) The stream offers no defect rates, incident history, or comparison with reviewing the code.
