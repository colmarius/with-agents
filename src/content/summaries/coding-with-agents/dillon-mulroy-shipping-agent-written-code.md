Dillon Mulroy describes a workflow in which agents write most of the implementation, but he still chooses the architecture, steers the context, and reads every line. His practical contribution is a way to agree on the shape of a change before generating it: types, call paths, error cases, and planned tests, followed by local review in small increments.

Productivity and organizational claims are the speakers' accounts. ### Main takeaways

- **Delegating implementation does not delegate accountability.** [08:19–11:21](https://www.youtube.com/watch?v=sYNOgpDKTvE&t=499s): Mulroy distinguishes his workflow from leaving agents running unattended and accepting their commits. He says he reads every line and applies the same engineering principles and experience as before; the means of producing the code changes, not the person responsible for its effects.
- **More output can coexist with less satisfaction and more fatigue.** [13:28–17:45](https://www.youtube.com/watch?v=sYNOgpDKTvE&t=808s): he previously alternated large design decisions with smaller implementation problems that supplied frequent moments of progress. Agents remove much of that second activity, leaving a succession of demanding design decisions without the same flow. This is his explanation of his own experience, not a measured effect for all developers.
- **Training engineering judgment remains an open problem.** [19:53–22:52](https://www.youtube.com/watch?v=sYNOgpDKTvE&t=1193s): both speakers learned through implementation mistakes and production failures. Mulroy attributes architectural intuition to seeing many patterns succeed and fail, but offers no settled replacement for that learning process when newcomers can prompt past the struggle.
- **Broader participation does not make specialties interchangeable.** [26:43–34:49](https://www.youtube.com/watch?v=sYNOgpDKTvE&t=1603s): Mulroy describes agents generating Playwright tests and recordings for changes, and product managers making prototypes to communicate ideas to engineers. Wortmann questions whether this implies one person can do every role; Mulroy agrees that a useful prototype is not a production-ready change and that skilled product management retains distinct value.
- **Expensive autonomous loops are not his default workflow.** [34:49–40:10](https://www.youtube.com/watch?v=sYNOgpDKTvE&t=2089s): Mulroy argues that the token budgets and uneven results of lab-promoted workflows make them impractical for many developers. He wants stronger evidence of consistent quality before treating those workflows as generally economical. This is a dated assessment, not a current price comparison or benchmark.

### The workflow in detail

- **Keep the harness stable enough to learn its behavior.** [45:47–48:56](https://www.youtube.com/watch?v=sYNOgpDKTvE&t=2747s): his tools include Ghostty, Herdr, Pi, and Plannotator. He values Pi's small system prompt and limited tool set because changes to a harness—the instructions and tools around the model—can change its behavior even when the model stays the same. He prefers modest customization and less automatically injected context.
- **Review locally before asking the team to review.** [48:56–51:01](https://www.youtube.com/watch?v=sYNOgpDKTvE&t=2936s): Plannotator presents a local diff with file-level review comments that feed back into the agent session. Mulroy keeps individual changes around 300–800 lines so he can understand them without his attention collapsing. Stacked pull requests let a later change build on an earlier, still-unmerged branch while keeping each review scoped; the line range is his working preference, not a universal quality threshold.
- **Build shared understanding before freezing a spec.** [51:01–53:08](https://www.youtube.com/watch?v=sYNOgpDKTvE&t=3061s): he annotates either a Markdown document or the agent's latest message and returns that feedback to the conversation. The discussion gradually becomes a spec; he writes it to a file and starts implementation only once he trusts that they agree on what to build.
- **Use conversation branches to control which research enters the working context.** [53:08–55:08](https://www.youtube.com/watch?v=sYNOgpDKTvE&t=3188s), [58:04–1:01:12](https://www.youtube.com/watch?v=sYNOgpDKTvE&t=3484s): he asks questions whose answers he already knows about libraries or existing abstractions, checks the agent's understanding, and develops separate branches for topics such as Hono and SQLite storage in Durable Objects. Pi's `/tree` lets him return to an earlier conversation point with no summary, an automatic summary, or a prompted summary. He often copies a selected conclusion or saves it to Markdown. This changes conversation context, not Git history. His preference over subagents is control over the returned evidence, not a claim that subagents cannot isolate research.
- **Make the spec describe code structure, not only product requirements.** [54:02–57:01](https://www.youtube.com/watch?v=sYNOgpDKTvE&t=3242s): his specs contain TypeScript types, interfaces, required adapters, and a call path showing inputs, outputs, and possible errors at each step. He also asks for the tests the agent will write using a red–green–refactor cycle. He trusts agents more with implementing a bounded function than with choosing and composing abstractions, so he spends the planning effort on those boundaries. He explicitly says this still requires correction; the approach does not eliminate mistakes.
- **Automating his steering process is a proposal, not the current result.** [1:02:03–1:04:31](https://www.youtube.com/watch?v=sYNOgpDKTvE&t=3723s): Mulroy imagines a queue that moves work through technology exploration, spec drafting, and review, with him involved at each stage. He is trying to capture recurring design preferences in skills so an automated first review can remove repetitive corrections. His near-term goal is saving some review time, not replacing human judgment.
