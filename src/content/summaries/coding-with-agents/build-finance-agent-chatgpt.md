OpenAI's Stefano Fabbri and Oliver Steffmann use a wealth-management workshop to explain how developers can extend an existing agent application with financial data, reusable instructions, and custom interfaces. The engineering choice is whether to build a separate application around an API or package a workflow inside the application employees already use. The latter can reuse deployment and access controls, but still requires integration code, permissions, and evaluation.

This summary is based on English auto-generated captions. Product availability, performance, and customer outcomes are the presenters' accounts at the time of the workshop, not independently verified results or current product documentation. The session does not establish that generated financial analysis is accurate or suitable for investment decisions.

### Key points

- **Connect data, analysis instructions, and output formats.** The workshop's wealth-advisor example moves from a portfolio change to explaining its causes and preparing a client presentation. The presenters describe three supporting pieces: financial data, domain-specific workflows, and artifacts such as spreadsheets and slides. Existing templates provide an output reference rather than requiring the model to invent a format for each analysis. - **Explain the data instead of only exposing it through an API.** Fabbri describes preprocessing datasets and supplying context about what fields mean and which information matters for a task. His examples include interpreting company filings and distinguishing market prices from returns. He characterizes the integration as customized tool access, not a claim that custom embeddings alone solve the problem; the underlying data structures are not exposed for workshop participants to inspect. [30:32–35:50](https://www.youtube.com/watch?v=ZJjRgvjhq3M&t=1832s)
- **Choose the host application before designing the integration.** A standalone API application needs its own interface and deployment lifecycle. A plugin can instead extend an enterprise application employees already have, using its existing deployment and access-control mechanisms. The workshop describes different capabilities across web, desktop, and CLI: built-in financial data was web-only, while UI extensions were desktop-only. Those restrictions qualify the proposed reuse; the interfaces were not interchangeable. [17:26–20:33](https://www.youtube.com/watch?v=ZJjRgvjhq3M&t=1046s), [27:27–29:37](https://www.youtube.com/watch?v=ZJjRgvjhq3M&t=1647s), [48:23–53:13](https://www.youtube.com/watch?v=ZJjRgvjhq3M&t=2903s)
- **Separate reusable instructions from executable integrations.** A skill supplies reusable instructions or knowledge. The presenters describe a plugin as a package that can also contain MCP connections, authentication logic, and UI components. MCP connects the agent to external tools and data; a skill alone does not implement that integration. UI extensions let builders customize parts of the host application, such as navigation or a client-meeting view. Backend hosting needs depend on what the plugin actually does. [53:13–58:17](https://www.youtube.com/watch?v=ZJjRgvjhq3M&t=3193s)
- **Maintain a small set of shared skills and measure model choices.** Historical reports and templates can guide repeatable output, but overlapping skills across a team become difficult to maintain. Steffmann recommends consolidating common capabilities and retesting behavior when models change. Fabbri suggests that well-specified recurring tasks may run on cheaper models, including cheaper subagents beneath a stronger coordinator; he explicitly ties that choice to use-case evaluations rather than assuming equivalent quality. [41:57–45:10](https://www.youtube.com/watch?v=ZJjRgvjhq3M&t=2517s), [1:02:42–1:08:03](https://www.youtube.com/watch?v=ZJjRgvjhq3M&t=3762s)
- **Reuse agent orchestration when it fits the workflow.** The team describes rebuilding a standalone financial-research application as a plugin. A planner divides a question into subquestions, research agents investigate independently, and a critique stage checks findings and sends contradictions back for more work. The motivation is to reuse the host's agent capabilities and let users change data sources and quality gates without leaving their working environment. This is a first-party architecture account, not evidence that replacing every deterministic step with agent decisions improves reliability. [1:09:09–1:14:10](https://www.youtube.com/watch?v=ZJjRgvjhq3M&t=4149s)
- **Keep permission controls around both the host and its tools.** Steffmann describes administrator-managed policies restricting local folders, network destinations, and plugin access. He places these alongside enterprise network and endpoint controls and explicitly says tools still need their own protection. Approval configuration must balance sensitive operations against repeated interruptions; the workshop does not demonstrate that sandboxing eliminates the risk of unsafe tool use. [1:27:53–1:32:09](https://www.youtube.com/watch?v=ZJjRgvjhq3M&t=5273s)
- **Build evaluations with domain experts before optimizing an agent.** Fabbri identifies the difficult part as translating business expertise into an engineering dataset. A single aggregate score hides where the agent fails. He recommends starting with simple checks before adding an LLM judge, so evaluator errors are easier to distinguish from agent errors. For model-based judgments, he favors decomposing broad ratings into yes-or-no questions. These are recommendations, not a benchmark comparing evaluation methods. [1:36:43–1:41:54](https://www.youtube.com/watch?v=ZJjRgvjhq3M&t=5803s)
- **Keep the system of record separate when the business requires it.** In the closing discussion, a colleague describes a proxy-voting workflow whose user interface lives in Codex but whose reports, dates, sources, and findings are written through tools to an external application database. Fabbri adds that regulated workflows need stored logs connecting decisions to their inputs and reasoning. Local files can preserve working state, while authenticated external tools handle persistence in the business system; producing a final report alone is not the audit trail they describe.
