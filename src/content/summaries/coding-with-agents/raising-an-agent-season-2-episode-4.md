Quinn Slack and Thorsten Ball describe extending agent work beyond implementation into deployment checks, user follow-up, and operations. They also discuss Amp's recent outages and ask whether remotely running agents and task-specific software will make the personal computer less central to their work.

This summary is based on English auto-generated captions, with speaker attribution checked against the official episode transcript. Workflow examples and incident figures are the hosts' accounts, not independently verified results; predictions about devices and model capabilities remain speculative.

### Key Points Covered

- **Delegate follow-through, not just code changes**: Thorsten recounts an agent coordinating a change across three repositories. Quinn describes longer-lived threads that wait for deployment, identify affected users from feedback and logs, prepare follow-up emails, and monitor feature usage and errors. Their internal plugins provide the necessary access; the email example includes a human send-or-cancel review [02:52–08:55](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=172s).
- **Test instructions with cases that should and should not trigger them**: Quinn describes generating small evaluations after system-prompt changes, running scenarios across modes and models, and iterating on missed behavior. The same approach can test whether removing an instruction preserves the intended outcomes, rather than letting the prompt grow indefinitely [09:53–11:59](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=593s).
- **Preserve the reasons behind changes where agents can retrieve them**: The hosts say shared thread history lets agents recover earlier investigations, human intent, shipped fixes, and customer communication—not just commit messages. They argue for consistent team tooling because fragmented history and access configuration make that context harder to use; this is their experience, not proof that a multi-agent setup cannot work [10:55–13:40](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=655s), [35:29–37:33](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=2129s).
- **Evaluate whether agents discover the intended workflow unaided**: Thorsten describes adding production-performance tooling, then asking fresh orbs—isolated remote execution environments—to perform database-related tasks without naming the tool they should use. The coordinating agent reads their threads, checks tool selection and parameters, adjusts the setup, and repeats. The test targets natural adoption of a workflow, not compliance with an explicit reminder. His production-testing safeguards are described only at a high level, not as a generally safe recipe [13:40–17:58](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=820s).
- **Separate incident causes from assumptions about agent-written code**: Thorsten reports roughly 18–20 incidents over six weeks, grouped into upstream-provider problems, infrastructure issues, and shipped code defects. Examples include storage recovery, metrics collectors displacing storage workloads, expensive database queries, and a Git upgrade breaking commit signing. Quinn says code defects accounted for about a third of incident count but a smaller share of downtime and affected users. These are the team's retrospective estimates, not a controlled comparison of development methods [20:04–27:11](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=1204s).
- **Redundancy can change the product contract**: Quinn explains that sandbox providers differ in snapshot and resume support. Adding provider failover can force reduced functionality and still leave the problem of recovering an existing environment when its original provider is unavailable. More redundancy therefore adds compatibility and recovery decisions, not just spare capacity [26:09–28:15](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=1569s).
- **Make operational evidence useful before relying on agents during incidents**: Thorsten says misleading error logs can send agents toward the wrong cause, just as they can mislead an unfamiliar human operator. The team is working on actionable logs, access to the same metrics humans use, and explanations of component relationships. Quinn recommends starting outside an active incident: grant log access, investigate errors, fix them, and confirm after deployment that they disappear [32:27–36:33](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=1947s).
- **Task-specific tools challenge the need for a carefully maintained local desktop**: Thorsten contrasts manually scrubbing video and arranging screenshots in a design tool with an orb-built frame selector that inserts frames into a thumbnail template with a live preview. Combined with mobile dictation and remote work, examples like this lead the hosts to speculate that devices may become mainly input and display surfaces. They do not establish that local applications or computers are obsolete [37:33–41:23](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=2253s), [43:20–49:23](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=2600s).
- **Workflow defaults embody bets about model behavior**: Quinn contrasts queuing a message until an agent finishes with steering, which supplies it at the next available opportunity during work. He argues that steering gives the agent useful input sooner, while acknowledging that users can restore queuing. The hosts' expectation that queuing will fade is a forecast, not a demonstrated universal advantage [49:23–51:25](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=2963s).
