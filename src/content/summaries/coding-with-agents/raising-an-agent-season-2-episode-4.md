Quinn Slack and Thorsten Ball describe extending agent work beyond implementation into deployment checks, user follow-up, and operations. They also discuss Amp's recent outages and ask whether remotely running agents and task-specific software will make the personal computer less central to their work.

### Key Points Covered

- **Agents can follow a change through deployment and user follow-up**: Thorsten recounts an agent coordinating a change across three repositories. Quinn describes longer-lived threads that wait for deployment, identify affected users from feedback and logs, prepare follow-up emails, and monitor feature usage and errors. Their internal plugins provide the necessary access; the email example includes a human send-or-cancel review [02:52–08:55](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=172s).
- **Test instructions with cases that should and should not trigger them**: When the team changes Amp's system prompt, Quinn says Amp builds a small evaluation: synthetic prompts where the instruction should and should not apply, run across Amp's modes and popular models. It then iterates on the cases it missed. The same approach can test whether an instruction can be removed without changing the intended outcomes, instead of letting the prompt grow indefinitely [09:53–11:59](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=593s).
- **Preserve the reasons behind changes where agents can retrieve them**: The hosts say that because the team's work happens in Amp threads, agents can find earlier investigations, what people said about a change, shipped fixes, and customer emails. A commit message alone does not carry that context [10:55–13:40](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=655s). They favor one coding-agent product across the team so that everyone has the same history and the same production access. They acknowledge that an MCP setup can be shared across several agents, but say they have not seen one work as well as a single well-maintained agent [35:29–37:33](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=2129s).
- **Test whether agents use new tooling without a reminder**: Thorsten adds tooling that lets agents check how a database change performs in production, which is hard to judge anywhere else. He then has an agent start fresh orbs (isolated remote execution environments) and give them database tasks that do not mention the tooling. The coordinating agent reads their threads, checks whether they used the tool and with the right parameters, adjusts the setup, and repeats. He does not detail the production safeguards [13:40–17:58](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=820s).
- **Separate incident causes from assumptions about agent-written code**: Thorsten reports roughly 18–20 incidents over six weeks, grouped into upstream-provider problems, infrastructure issues, and shipped code defects. A storage-node failure required hours of data movement to restore redundancy; code incidents included queries that overloaded the database. Quinn says code defects accounted for about a third of incident count but a smaller share of downtime and affected users. These are the team's retrospective estimates, not a controlled comparison of development methods [20:04–27:11](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=1204s).
- **More redundancy is not a simple fix for outages**: Quinn explains that sandbox providers support different features: some offer memory snapshots, and some cannot resume an environment. Failing over between providers could mean accepting a slower product with fewer features, and it still leaves open how to recover an existing orb when its original provider is down. He concludes that adding redundancy brings hard compatibility and recovery decisions [26:09–29:17](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=1569s).
- **Make operational evidence useful before relying on agents during incidents**: Thorsten says misleading error logs can send agents toward the wrong cause, just as they can mislead an unfamiliar human operator. The team is working on actionable logs, access to the same metrics humans use, and explanations of component relationships. Quinn recommends starting outside an active incident: grant log access, investigate errors, fix them, and confirm after deployment that they disappear [32:27–36:33](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=1947s).
- **Task-specific tools challenge the need for a carefully maintained local desktop**: Thorsten contrasts manually scrubbing video and arranging screenshots in a design tool with a teammate's orb-built frame selector that inserts frames into a thumbnail template with a live preview [37:33–41:23](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=2253s). Thorsten also describes dictating tasks on a walk and checking the resulting agent threads afterward. These examples lead the hosts to speculate that personal devices may mainly capture input and display results while more work runs remotely [43:20–49:23](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=2600s).
- **Amp now passes mid-task messages to the agent by default**: Quinn says Amp changed what happens to a message sent while the agent is working. The old default, queuing, held the message until the agent finished. The new default, steering, injects it at the next available opportunity during the work. He argues that steering gives the agent more of the user's input sooner. Some users say their workflows still need queuing, which remains configurable, but the hosts predict it will fade [49:23–51:25](https://www.youtube.com/watch?v=7pstrDQ4xLs&t=2963s).
